# 前端面试题库（程宇轩 · 4年 · 杭州 18-25K · 含参考答案）

> 依据候选人简历定制：4 年经验（飞猪 / 航天时代 / 安恒），B 端后台 + 可视化大屏 + 三维 GIS + 组件平台 + 前端 PM，另有「AI 智询平台」与 Trae/Cursor/Claude Code 经历。
> 建议 60-75 分钟（业务 20 / 技术 40 / 反问 10）；**必问** 标在题前；每题为面试官评分参考要点。简历原文见 `~/Downloads/【前端开发工程师_杭州+18-25K】程宇轩+4年.pdf`。

## 一、业务面

### A. 经历与动机（约 5 分钟）

1. 4 年经历飞猪（1 年 2 个月）→ 航天时代（约 10 个月）→ 安恒（约 9 个月），每段都不长，每次变动的决策依据是什么？
   - 无标准答案。期待：每段有明确诉求变化（业务方向/技术深度/角色），且能坦诚承认部分选择失误。
   - 警惕：全怪公司/领导；说法前后矛盾；对"稳定性"问题毫无自觉。
2. 2022.07 硕士毕业到 2023.07 入职飞猪之间约一年、2024.09→2024.12 约 3 个月，这两段在做什么？
   - 听解释是否自然（备考/待业找方向/家庭/项目空窗等均可），重点是不慌乱、可核实（与后续背调一致）。
3. 低空、安全、客服这类 B 端/政企方向，如果下一份不是这个方向，可迁移能力是什么？
   - 期待拆解三层：业务可迁移（复杂表单/权限/数据链路）、技术可迁移（工程化/性能/组件化）、领域知识不可迁移但学习路径清晰。

### B. 业务理解与数字口径（约 10 分钟）

4. **必问** 「低空服务管理效率提升 40%+」「年度节省成本 50w+」「降低转人工率 3%-10%」，挑一个讲：数字怎么来的？
   - 期待：说得出分子分母、统计周期、数据来源（埋点/报表/业务方估算）、有无对照；能主动区分"我测算"与"业务方给的"。
   - 扣分：全部推给业务方；说不出任何口径。
5. 低空监管：无人机从"产生告警"到"前端呈现"到"人工处置"的完整链路？前端最易丢消息或延迟的环节在哪？
   - 参考链路：规则引擎/算法产生告警 → MQ/WS 推送 → 前端告警中心（列表/地图打点/声光提示）→ 人工认领-处置-归档。
   - 前端风险点：WS 断连丢事件（重连 + 增量对账兜底）、页面后台化定时器节流、高频告警渲染压力、地图点位聚合。
   - 加分：「漏报比误报更致命，要有兜底轮询对账」。
6. 机场客户面向市领导演示："需求完成度 100%"的验收标准是什么？演示前一天关键功能不可用怎么决策？
   - 期待：验收清单化（逐条验收/客户确认）；演示前 checklist + 预演；降级预案（静态数据兜底/录屏备播）；先保核心叙事再修细节。
7. C 端客服小蜜卡片：降低"转人工率"和保住转化天然矛盾，你改过哪张卡？效果怎么验证？
   - 期待：具体卡片 + 指标设计（转人工率/自助解决率/满意度/卡片点击率）+ 灰度或 A/B 验证 + 引导不骚扰（频次控制）。
   - 加分：「降转人工不能靠藏入口，要靠高频问题自助化」。
8. 组件平台 30+ 组件：跨团队推广最大阻力？回头看哪里能做得更好？
   - 期待：阻力类型（跨团队信任/定制诉求/接入成本/维护归属）+ 手段（文档/demo/脚手架/陪跑）+ 反思（先做被复用最多的 2-3 个，别求全量；版本兼容策略提前定）。
   - 加分：「组件不是越多越好，维护成本是负资产」。

### C. 项目管理与协作（约 5-8 分钟）

9. **必问** 作为前端 PM 带 3 人小组：任务怎么拆、排期怎么定、风险怎么暴露？举一次险些/已延期的经历。
   - 期待：拆任务（按模块/按人能力）+ 排期（buffer、依赖倒排）+ 风险机制（站会/看板/阻塞项升级）；延期案例讲清原因、判断、应对（砍范围/顺延）、复盘。
   - 扣分：只讲 Jira 不讲决策；把"没延期"当唯一成功标准。
10. 「研发链路优化」节省前端 1 人 + 后端 0.5 人：具体改了什么？"节省"怎么验证？
    - 期待：环节具体化（重复人工自动化/脚手架/CI/联调流程）+ 折算方法（工序耗时 × 频次 → 人天）；坦承估算局限。
11. 与产品/后端分歧时，举一个推动达成一致的例子。
    - 期待 STAR：背景-分歧-动作（找数据/拉评审/给替代方案）-结果；先理解对方约束，用数据或原型说服。
12. Trae/Cursor/Claude Code 在团队怎么用？实际效率改变？翻车案例？
    - 期待：具体场景（样板代码/单测/解释代码/排错）+ 哪些快了哪些没快 + 事故（幻觉 API/风格漂移）+ 团队规则（人工 review、敏感代码不外传）。

## 二、技术面

### D. 可视化大屏与三维（约 15 分钟）

13. **必问** 多个大屏怎么适配不同分辨率（含超宽屏/小间距 LED）？等比缩放后文字变糊怎么处理？
    - 期待：基准分辨率（1920×1080）+ `transform: scale` 整屏等比缩放（主流）；缺点：非等比留白/裁切、字变糊（文字类改 canvas 渲染或按缩放系数反算字号、ECharts 设 `devicePixelRatio`）；超宽屏弹性布局 + 局部固定比例混合。
    - 加分：分辨率适配与内容布局解耦（媒体查询/容器查询 + 缩放混合）。
14. **必问** 实时大屏 10+ 图表 + 高频刷新怎么不卡？说实际用过的优化。
    - 期待组合拳：渲染层（ECharts `setOption` 增量更新 `notMerge:false`、大数据量换 canvas/WebGL renderer、DOM 虚拟化）、数据层（降采样/差分更新/合并批量）、调度层（统一 rAF/定时器池、页面隐藏暂停、WS 消息节流合并）、内存层（组件销毁 dispose、监听解绑）。
    - 加分：给量级（"5000 点轨迹 60fps"）与验证方法（Performance 面板）。扣分：只会"防抖节流"四个字。
15. Cesium/Mars3D：单场景多少模型/图层？做了哪些渲染优化？反复进出页面怎么排查内存泄漏？
    - 期待：3D Tiles 分块 + LOD、primitive 替代 entity（entity 是上层封装，量大时性能差）、贴图压缩、视锥剔除、距离显隐、销毁释放（viewer/tileset destroy、监听移除）；排查：反复进出页面看 Performance/Memory 快照、WebGL 上下文是否丢失。
16. 无人机实时轨迹：数据频率与推送方式？轨迹平滑与断连补偿？几十架同屏怎么控制开销？
    - 期待：概率 1-5s 级、WS 为主轮询兜底；平滑 = 时间戳 + 插值（线性/样条）补间；断连重连后拉全量快照对账；多机：合批/按距离降频/低频用 entity 高频用 primitive。
    - 加分：「位置数据必须带时间戳才能正确插值」。
17. 离线地图：为什么必须离线？瓦片怎么部署加载？坐标系偏移怎么处理？
    - 期待：内网/涉密不出公网；自建瓦片服务（静态目录/nginx、MBTiles）、按层级与区域裁剪、体积规划；加载替换地图源为本地 URI/内网地址；坐标系：Cesium 用 WGS84，Leaflet 接高德/腾讯瓦片有 GCJ-02 偏移需纠偏（或直接用天地图 CGCS2000≈WGS84）。
18. Leaflet 大量设备/人员点位怎么不卡？点击命中怎么做？
    - 期待：点聚合（markercluster/supercluster）、`L.canvas()` 替代 SVG、超大场景 WebGL（deck.gl/glify）、按视野 bbox 分片加载；命中：聚合层展开或几何索引。
    - 加分：「点位 1 万以上 DOM 方案直接放弃」。

### E. Vue 与组件化（约 10 分钟）

19. Vue3 vs Vue2 响应式原理？ref/reactive 的坑？shallowRef/markRaw 用在哪？
    - 期待：`Object.defineProperty`（递归劫持/数组 hack/新增属性不响应）→ `Proxy`（惰性、可监听增删与索引）；坑：解构 reactive 丢响应（toRefs）、ref 需 `.value`、整体替换 reactive 对象；shallowRef 用于大对象/只整体替换场景；markRaw 用于 Cesium viewer、ECharts 实例等不应被代理的对象。
20. 组件平台配置化：schema 怎么设计？升级不破坏已有大屏？运行时性能？
    - 期待：schema = 组件类型 + props + 数据源 + 布局（JSON）；渲染器 type→组件映射 + 数据适配层；兼容：schema version + 迁移函数、props 只增不改、deprecated 标记；性能：按需/懒加载、避免深层 watch（watch 指定路径）。
    - 加分：「配置化适合同结构不同数据，不是把所有定制都塞 schema」。
21. 封装最复杂的 Ant Design 组件：受控/非受控、透传、插槽、升级冲突怎么处理？
    - 期待：具体案例（带搜索/分页/多选的表格等）；`value + onChange + defaultValue` 三件套、`$attrs`/事件透传不漏、插槽扩展点；升级：锁主版本、二次封装留逃生舱（暴露原实例/允许 raw props）。
22. Vuex 与 Pinia 差异？高频更新的跨模块实时数据状态怎么设计才不整树重渲？
    - 期待：Pinia 去 mutation、TS 友好、扁平模块、组合式 API；高频数据不进全局大对象（shallowRef + 局部订阅）、隔离到最小组件、Cesium/ECharts 对象直接命令式更新绕过响应式、computed 缓存派生。
    - 加分：「响应式不是免费的，60fps 数据流绕过 reactivity 直接操作渲染对象」。

### F. 工程化与发布（约 8 分钟）

23. webpack 与 Vite 原理差异？老 Vue 项目迁 Vite 的步骤与风险？
    - 期待：webpack = bundle-based 全量构建（loader/plugin 生态）；Vite dev = 原生 ESM + esbuild 预构建（秒级启动）、build = Rollup（新版 Rolldown 可选）；迁移：版本对齐 → 配置等价（alias/define/env/proxy/多页）→ CJS 依赖与 polyfill → 环境变量与 public → 产物对比 → CI/部署。风险：CJS 插件不兼容、动态 require、全局 scss 注入、base 路径。
24. npm 私仓组件：版本策略？按需引入与 tree-shaking 怎么保证？有单测/文档吗？
    - 期待：semver（break=major）、beta tag 预发布、不可变版本；按需：ESM 产物 + `sideEffects: false` + 子路径 exports；tree-shaking 前提（ESM/无副作用）；文档 storybook/dumi + 核心逻辑单测。
    - 加分：灰度（next tag + 指定团队试装）。
25. 从提交到上线的流程？客户内网/离线部署与普通 Web 差别？灰度与回滚？
    - 期待：提交 → CI（lint/test/build）→ 产物 OSS/CDN 或镜像 → 部署 → 灰度（按用户/流量）→ 监控 → 回滚（保留上版产物秒切）；离线：内网 GitLab/私仓/离线 npm 源/私有 registry，更新走客户审批窗口。

### G. 基础与手写（约 5-8 分钟，选 2 题）

26. 事件循环输出题（Promise/async/定时器混合，可包"大屏批量刷新"场景）。
    - 期望：准确排序 同步 → 微任务（Promise.then，注意 await 之后 = 微任务）→ 宏任务（setTimeout）；Promise 构造器内同步执行。考察口头推演，面试官现场写一题即可。
27. 手写 `requestPool(urls, maxConcurrent)`：并发上限、失败重试、结果顺序。
    - 参考实现：running 计数 + 队列；完成一个从队列取下一个；结果按索引回填保序；错误策略（fail-fast 或 allSettled）；边界：max<=0、空数组。延伸问重试（指数退避）——贴他分片拉取（并发 3）经历。
28. 设计题（二选一）：大表格虚拟滚动；或素材缓存 + LRU。
    - 虚拟滚动：可视区索引计算（scrollTop/行高）、上下占位、行高不定需测量缓存、滚动节流、key 稳定。LRU：Map 实现（get 后 delete+set 移到尾部）、超限删首 key。看是否写过真实代码。
29. SSE vs WebSocket？LLM 流式问答为什么常 SSE？打字机流畅渲染与中断重试？
    - 期待：SSE 单向 server→client、HTTP 长连接、自动重连（Last-Event-ID）、易过代理；WS 全双工/二进制/要自己心跳。LLM 输出单向 → SSE 更轻；打字机：rAF 批更新（勿每 token setState）、Markdown 增量解析、上滚暂停跟随、AbortController 中断、重试需幂等 ID 防重复计费。

### H. AI 应用开发（大模型产品，约 10-12 分钟）

30. **必问** 「AI 智询平台从 0 到 1」：整体架构？前端/BFF/模型服务怎么分工？模型选型为什么？
    - 期待分层：前端（会话 UI/流式渲染）→ BFF/网关（鉴权/限流/SSE 透传/上下文拼装）→ 模型服务（自部署 vLLM 或 API）+ 知识库（向量库+检索）。
    - 加分：能说清选型理由（自部署 = 数据不出内网/成本可控；API = 快速起步）；SSE 透传坑（Nginx buffering off、超时）。
31. 从发送到「首 token 返回」经过哪些环节？TTFT 慢从哪查？
    - 期待分段定位：前端网络时间线 → BFF（排队/鉴权/检索耗时）→ 模型（prompt 长度/排队）。
    - 常见根因：Nginx 缓冲导致"看起来没流式"、网关一次性读取、RAG 检索慢、prompt 过长。
32. 流式渲染细节：Markdown 增量渲染与高亮？长回答不卡？上滚时新内容到达怎么处理？
    - 期待：Markdown 增量解析（缓冲突 token/未闭合标签）、代码高亮延后或降级防卡、长文分块/虚拟化 + memo 减少 re-render；滚动策略：仅当接近底部才跟随，否则暂停并显示"回到底部"。
33. 「文档智能管理」具体做了什么？你负责哪段？"引用出处"怎么呈现？
    - 期待链路：上传（分片/进度）→ 解析（PDF/Word，OCR 可选）→ 切分（按标题/长度/重叠）→ 向量化 → 检索（向量+关键词混合、rerank）；前端：文件管理 UI、解析进度、引用呈现（点引用跳原文/高亮）。
    - 加分：「引用要带文件名+段落出处，才能降低幻觉信任成本」。
34. 多轮上下文怎么管理？token 预算谁控？usage/计费信息前端怎么展示？
    - 期待：保留近 N 轮 + 超长摘要、system prompt 固定；token 预算一般后端控（保 prompt 完整性），前端展示用量与超限提示；usage 随流式末条/单独事件返回。
35. 中断与失败：停止生成、网络断开、重试会不会重复计费？断线后消息怎么续传？
    - 期待：停止 = AbortController 断流 + 已生成内容落库标记；断网区分可重试；防重复计费 = 服务端消息 ID 幂等、重试沿用同 request ID；续传 = 重连拉取最新状态（后端存流式快照）。
    - 加分：「LLM 请求天然非幂等，要服务端配合」。
36. AI 回答质量怎么度量？前端埋点什么？"差评→优化"闭环怎么设计？
    - 期待：指标（点踩率/追问率/复制率/TTFT/引用点击率）+ 消息维度 ID 关联埋点 + 差评归因分类（答非所问/不全/幻觉）→ 补知识库/调 prompt/回归评测。
    - 加分：不用点赞率当唯一指标（讨好型回答会刷高）。
37. 幻觉与合规：怎么提示不准确？内部文档场景，prompt 注入/信息外发风险，前端能做什么？
    - 期待：产品层引用溯源 + 免责声明；输入侧注入检测/敏感意图拦截、输出侧过滤脱敏；合规：内部文档不出域（自部署/私有网关）；前端：数据用途明示、会话权限隔离、水印、导出限制。
38. 开放设计题：给低空监管平台做「AI 态势助手」（自然语言查空域/航班/无人机数据），怎么设计？
    - 期待：入口（侧边问答/指挥台）→ 意图 → function calling（查航班/无人机/告警）→ 后端编排（权限校验/数据脱敏）→ 流式回答 + 结构化卡片（回答带"定位到地图"动作）；过程态（正在查询…、可取消）；分工：前端管交互与过程呈现，模型编排在后端。
    - 加分：「数据查询权限必须走用户身份，不能靠模型兜底」。

### I. AI 辅助研发（约 8 分钟）

39. **必问** Trae/Cursor/Claude Code：各举一个"帮大忙"和"帮倒忙"案例，适用边界？
    - 期待：「帮大忙」= 样板代码/单测/正则/陌生 API 速查/小步重构；「帮倒忙」= 幻觉 API/版本、越权改动、并发与边界错误、简单问题复杂化。
    - 边界感：确定性高、可验证的适合；跨模块架构决策/安全敏感/重业务上下文的谨慎。加分：有"AI 出方案、人审"的固定流程。
40. AI 生成代码怎么把关？团队有没有"禁止 AI 直改"的规则？
    - 期待：编译/类型/lint/单测四道闸 + 人工 review；重点盯依赖引入、网络请求、错误处理、边界；规则：敏感仓库不外传、生成代码同门禁、CIs 不特殊放行。
41. 怎么防止 AI 编造 API/依赖版本？怎么给它喂上下文？
    - 期待：让 AI 读本地上下文（源码/类型/lockfile/官方文档）+ source-driven（以文档为准）+ 版本锁定 + 写完立即跑验证；工具侧：索引、rules 文件、引用式提问。
    - 加分：要求 AI 输出"验证方式（命令/测试）"而非只输出代码。
42. 10 人团队落地 AI 编码工具：选型、规范、度量、风险？
    - 期待：选型（技术栈/合规）→ 试点（1-2 组 + 成功指标）→ 规范（可用/禁用场景、代码归属与审查）→ 度量（PR 周期/缺陷率，别只看代码行数）→ 风险（合规、数据安全、能力退化）。
    - 加分：「先改流程再上工具」。
43. AI 工具改变了哪些研发环节？哪里最好、哪里最差？
    - 期待：收益大 = 样板/测试/解释遗留代码/排错辅助；收益小 = 需求澄清、跨系统架构决策（缺业务上下文与责任主体）。加分：有自己的"人机分工"模型。

### J. Monorepo 基础与选型（约 6 分钟）

> 注：简历未写 monorepo（只有 npm 私仓 + 组件平台），本组判断其组件平台工程化含金量与引入/驾驭 monorepo 的能力。

44. **必问** 组件平台是 monorepo 还是"每组件一 repo + npm 私仓"？两者优劣？为什么这么选？
    - 期待：多 repo = 独立版本/权限清晰/CI 简单，但联动升级痛、依赖漂移、原子变更难；monorepo = 原子提交/统一工具链/依赖收敛/重构易，但 CI 复杂/权限粗/仓库膨胀。
    - 选型依据：组件复用度、团队规模、发布节奏。加分：混合方案（组件库 monorepo + 业务多 repo）。
45. pnpm 的 node_modules 结构？为什么 monorepo 常用 pnpm？
    - 期待：全局 store + 硬链接（同版本共享磁盘）+ `.pnpm` 虚拟目录 + 符号链接（包只能"看到"自己声明的依赖）；npm/yarn v1 扁平化 hoisting（幽灵依赖、结构不确定）；pnpm = 严格隔离 + 快 + 省盘。加分：懂 `shamefully-hoist` 取舍。
46. 幽灵依赖是什么？怎么防？踩过吗？
    - 期待：用了没写进 package.json 的包（靠 hoisting 恰好可见），换包管理器/升级即炸；防：pnpm 严格模式、`--strict-peer-dependencies`、depcheck/eslint no-extraneous-dependencies。加分：真实案例（切 pnpm 后构建挂）。
47. 同库不同大版本冲突怎么处理？
    - 期待：两版本同时装入 → 运行时"双实例"（React/antd 双实例 hooks 报错/样式炸）；收敛：overrides/resolutions 统一、peerDependencies 声明、推动升级；不能收敛则确认无状态并存是否可行，否则强制统一。

### K. Monorepo 落地深化（约 8-10 分钟）

48. **必问** 内部公共包跨包引用：源码引用还是 dist 引用？各自踩过什么坑？
    - 期待：源码引用（dev 体验好/免构建，但工具链要求 TS 直引、构建慢）vs dist（稳定可发布，但改完要 rebuild、易 dist 过期 → tsc 假错，他正好踩过）；dev 可 watch 构建或条件导出（development 指向 src）。
49. A 包依赖 B 包且两个都在改：本地 dev 怎么让改 B 立即在 A 生效？
    - 期待：workspace 链接 + B watch 构建（tsc -w/tsup dev/turbo watch）+ A 热更新；或条件导出 dev 直接吃源码；避免用 yalc/npm pack 当日常手段。
50. `workspace:*` 是什么？发布时怎么变真实版本号？
    - 期待：表示用 workspace 内包；publish 时由工具链自动替换为当前版本（`workspace:^` → `^1.2.3`）；保证本地永远链接本地、产物带真实版本。加分：知道属发布工具链职责，手改易漏。
51. **必问** 改一个包会触发全量构建吗？turbo/nx 任务图、缓存、`--affected` 原理？CI 怎么不快崩？
    - 期待：任务图（包依赖 + pipeline）定顺序；内容哈希（源码+依赖哈希+环境变量）命中缓存直接跳过；affected = 对比 base 的 git diff 只跑受影响包；提速：远程缓存共享、filter install、并行。
    - 加分：知道缓存失效坑（环境变量/全局文件变更导致误命中或不命中）。
52. 多包版本：fixed 还是 independent？changesets/lerna 流程？break change 怎么灰度给接入方？
    - 期待：fixed（全仓同版本，简单，适合联动）vs independent（灵活，兼容矩阵复杂）；changesets：PR 记 changeset → 合并 → 版本 PR（自动版本+CHANGELOG）→ 发布；灰度：beta tag → 接入方试点 → 稳定推 latest。加分：破坏性变更提前一个版本 deprecate。
53. 把「多 repo + 私仓」迁到 monorepo：迁移路径、顺序、风险？
    - 期待：评估（依赖图/工具链/发布流程）→ 选型 → 渐进式（先收拢高频联动的 2-3 个包 → 新包直接进大仓 → 旧包逐步迁），避免大爆炸；风险：历史分支冲突、CI 重建、权限流程变更、团队心智。
    - 加分：「可以只把『联动发布』的组做 monorepo，其余保持独立」。
54. monorepo 的测试策略？缓存怎么保证正确（依赖图外的东西改了要失效）？
    - 期待：单包测试 + CI 跑 affected（受影响包及其上下游，turbo 依赖拓扑）；测试任务输入哈希含源码+依赖+环境；定时全量回归兜底。
55. 亲身感受到 monorepo 的哪些缺点？什么规模不适合上？
    - 期待：克隆/拉取慢、CI 排队与缓存管理成本、工具链强耦合、子包权限难精细、IDE 索引重；小团队/低耦合/独立发布节奏 → 多仓更简单。
    - 加分：「monorepo 是组织问题的技术映射，没那个痛别上」。

## 三、评分与红线

- **业务面**：数字是否可解释、PM 是否真带过人、三段离职理由与空档是否自洽。
- **技术面**：大屏/三维是卖点，必须答到实现细节与量级；Vue 不能只会用 API；手写题看边界与代码风格。
- **AI 方向**：只会罗列工具名/模型名；讲不清一次请求链路；把"个人用过 ChatGPT"包装成"负责 AI 系统"；对幻觉/计费/隐私无意识。
- **Monorepo**：只会喊"monorepo 好"；幽灵依赖/构建缓存/workspace 协议一个接不住；把"私仓发组件"当"维护过 monorepo"。
- **通用红线**：简历数字含糊其辞；只谈"用了什么库"答不出优化与坑；离职理由互相矛盾；PM 经历只有排期工具没有决策。
