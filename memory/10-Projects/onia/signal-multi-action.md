# Onia Signal 多动作串行与编辑页

本文是给评审用的产品文档，只覆盖 Social Proxy 产品线 Onia，不涉及 Verlume。对照 colna-memo 中的 [overview.md](overview.md)、[architecture.md](architecture.md)、[instagram-actions-pipeline.md](instagram-actions-pipeline.md) 以及 2026-11-12 工作日志写成。不改仓库、不写代码、不写飞书。实现方案交由技术架构师另出，本文只规定产品语义、范围、流程和验收标准。

文中不编造用量、转化、市场规模或耗时承诺。

## 1. 背景与现状（必须按此理解，不要写回旧口径）

截至本文撰写时，Onia 仍遵循「一条 Signal 只生成一种动作、一条 Todo」。不同动作可以在同一设备上并存，但不会由同一条 Signal 带出一串动作。

后台已有两类入口，语义不同，不要混为一谈：

- **「发令」页**（路由 `/commands`）：提交 `MANUAL_ACTION`，由运营手动指定**单个**动作和参数。可用动作包括 `get_profile`、`sync_profile`、`follow_user` 等已登记动作。走既有管线 Signal → Todo → Scheduler → Behavior，不直派 Behavior。
- **「创建 Signal」页**：目前只创建 `INBOX_ACTIVITY` / `PROFILE_SYNC_NEEDED` 这类来源事件，payload 是简单来源标记，**不是**选动作表单。这两种类型仍表示「收件箱有活动 / 需要同步资料」，可以和 `MANUAL_ACTION` 产出相同动作，但语义不同，本阶段不得删除。

技术方案 [instagram-actions-pipeline.md](instagram-actions-pipeline.md) 已写明：服务端下发「步骤数组」那种 `executePipeline` **本轮不做**；多步骤只存在于**单个动作内部**（例如 `send_message` 在脚本里跳转页面、pending 后续跑）。那是当时那一轮的约定，不是最终产品边界。

**本次是下一阶段的新需求**，会改变「一条 Signal 一个动作」的约定：一条 Signal 将包含多个动作，并且串行执行。这不是对上一轮方案的勘误，而是明确进入下一阶段。

动作名继续使用 Onia 的 snake_case，三侧同一套：

`get_profile`、`sync_profile`、`follow_user`、`pull_inbox`、`pull_thread`、`send_message`、`send_greet`、`like_post`、`comment_post`、`get_media_insights`、`create_post`、`create_story`

其中 **`create_post` / `create_story` 的实打上传尚未打通**。它们可以出现在编辑画布和发令选项里，但文档、界面和验收都不得写成「已经能发帖 / 发快拍」。live 路径下这两步当前会失败关闭，且不得回落演示数据、不得误报成功。本阶段不把打通上传列为必须完成的目标。

`inbox.send_reply.v1` / `send_reply` 仍不在控制台出现，留给后续 Agent。

## 2. 目标

让运营在后台用可视化方式编排一条「多动作、严格串行」的 Signal，再选择已绑定设备发送；发送后能按步骤看到执行进度和结果。单动作发令和来源事件入口在本阶段仍可用，不被这次改动弄坏。

成功不看用量或转化，只看：编排能保存、发送能落到既有管线、串行语义正确、失败会停住后续步骤、旧入口和单动作 Signal 仍然成立。

## 3. 范围与非目标

### 本阶段要做

- 新建「Signal 编辑」页：流程图画布，支持从动作列表拖拽到画布、调整顺序、配置每个节点的参数，交互对标常见低代码编排（画布 + 节点面板 + 选中后的参数面板）。
- 将当前「创建 Signal」页改名为「发送 Signal」页，并承担「把已编排的 Signal 下发到指定设备」的主路径；同时保留发送 `INBOX_ACTIVITY` / `PROFILE_SYNC_NEEDED` 来源事件的能力。
- 一条已发送的 Signal 可以包含 1 到 N 个动作，按编排顺序串行执行。只含一个动作的 Signal，在结果上等价于今天的单动作 `MANUAL_ACTION`。
- 追踪页能按 `signal → 各步骤的 Todo / Behavior` 看到每一步的动作名、参数摘要、状态和结果，而不是只看到 UUID。
- 明确失败、中断、重试，以及与 Todo / Behavior 的关系（见第 8、9 节）。

### 本阶段不做

- 并行、条件分支、循环、汇合，以及「等待 / 延时」节点。
- 步骤之间的变量引用或自动把上一步结果填入下一步（例如 `{{step1.user_id}}`）。
- 把「发令」页改成流程图，或在本阶段撤掉「发令」页。
- 打通 `create_post` / `create_story` 实打上传。
- Agent、`send_reply`、脚本 OTA、获客漏斗包本身的实现或改造。
- 要求客户端必须上线服务端下发的 `executePipeline` 步骤数组。产品要的是「一条 Signal 里多个动作串行执行」；默认按第 8 节的管线展开来满足，实现方案由技术架构师确认，不在本文里锁死客户端协议形态。

## 4. 用户与场景

主角是已登录 Onia 后台的运营（含本人联调）。设备必须是已绑定真实 Instagram 账号的设备；离线仍允许提交，Todo 保持 pending，离线不是失败。

典型场景：

1. 运营要先查某个用户资料，再关注，再从主页打招呼。以前要发三条互不所属的 Signal，顺序靠人盯；现在在编辑页排成一条链，发送一次，系统按成功顺序往下走。
2. 同一套步骤以后还要对别的设备再发一次：编辑页保存的是**不绑定设备的定义**，发送时再选设备。
3. 联调或临时只要一个动作：继续走「发令」页，不必先画流程图。
4. 仍需手动制造「收件箱有活动 / 需要同步资料」这类事实时，走「发送 Signal」里的来源事件，而不是去选动作。

## 5. 编辑与发送如何分工

| 页面 | 职责 | 不做什么 |
|------|------|----------|
| **Signal 编辑** | 编排并保存「Signal 定义」：名称、有序动作节点、每个节点的参数。可新建、打开、另存、删除未在发送中的定义。可以从编辑页进入「保存并去发送」，跳到发送页并预填该定义。 | 不选择设备，不创建已发送的 Signal 实例，不调用下发。定义未保存则不能发送。 |
| **发送 Signal**（由「创建 Signal」改名） | 两类发送：① 选择一条已保存的 Signal 定义、选择已绑定设备及其当前账号，确认后创建并下发一条 Signal **实例**；② 发送来源事件 `INBOX_ACTIVITY` / `PROFILE_SYNC_NEEDED`（保留原能力）。发送成功后跳到既有追踪页，带上 `signal_id`。 | 不在这个页面里画流程图，不把动态动作表单整页搬过来（单动作快捷入口仍在「发令」）。 |
| **发令** | 见第 7 节，本阶段保留为单动作快捷入口。 | 不支持多动作。 |

关键规则：

- **定义与实例分开。** 编辑页保存的是可复用定义；发送时对当时的步骤和参数做一次快照，生成 Signal 实例。之后再改定义，不影响已经发出去的实例。
- **设备在发送时选择，不在编辑时选择。** 实例一旦创建，`device_id` 仍不可改，与现约定一致。
- **服务端写入的身份字段**（`platform`、`account_id`）在发送时写入各步骤 params，不出现在编辑表单里，脚本不得采信客户端自报的「自己」。
- 同一次点击的重试沿用同一 `idempotency_key`；运营再次主动发送用新键，避免关注、点赞、私信被静默吞掉。
- 导航文案：「创建 Signal」改为「发送 Signal」。旧路由应能跳到新页面，避免书签失效。

## 6. 流程图：节点、连线与串行含义

编辑页采用低代码常见布局：

- 左侧：动作面板，列出第 1 节白名单动作，显示 Onia 动作名并旁注中文（例如「关注用户 `follow_user`」）。`create_post` / `create_story` 必须带可见说明：实打上传尚未打通，live 下发后会失败，不会误报成功。
- 中间：画布。支持把动作拖到画布成为节点，拖拽调整顺序，删除节点，复制节点。
- 右侧：选中节点后的参数面板，按该动作的既有 params 契约展示必填 / 选填项。

节点表示一个动作步骤，包含：步骤序号、动作名、参数是否已填完。本阶段没有网关、条件或子流程节点。

连线只表示**串行先后**：`A → B` 的含义是「A **成功结束后**，才开始 B」。连线不携带条件，也不表示并行。

本阶段画布在产品上必须是**一条单链**：一个起点、一个终点，中间无分叉、无汇合、无环、无孤立节点。保存或进入发送前，若图不是单链，要明确报错并挡住，而不是静默改成运营没见过的顺序。可用「自动排成一条竖向/横向链」降低误操作，但不允许运营画出并行分支却当作串行发出去。

一条定义至少包含 1 个节点。空画布不能保存为可发送定义，也不能发送。

串行执行含义（对已发送实例）：

1. 只有第 k 步达到成功终态后，第 k+1 步才开始调度。
2. 第 k 步仍在执行、pending（动作内部跳转续跑）、或因设备离线而等待时，不算失败，后续步骤不得提前开始。
3. 第 k 步最终失败，则 k+1 及之后的步骤**不再执行**，并标记为取消（原因：前一步失败），而不是再标成失败。
4. 整条 Signal 成功，当且仅当所有步骤都成功。任一步最终失败，则 Signal 为失败。运营中途取消，则 Signal 为取消；已成功的步骤保持成功，不做业务回滚。

## 7. 参数如何配置，以及「发令」页是否保留

每个节点的参数配置复用「发令」页已经采用的契约（见 [instagram-actions-pipeline.md](instagram-actions-pipeline.md) 的 params / 结果表），包括必填与选填、类型与校验。例如：`get_profile` / `follow_user` / `send_greet` 必填 `target_handle`；`send_message` 必填 `target_handle` 与非空 `texts`；点赞 / 评论必填 `short_code` 或可解析的 `post_url`，评论另必填 `content`。表单不出现 `sessionid`、`chunk_base`、`result_url`、`result_token`。校验必须在服务端执行，不能只靠前端。

本阶段各步骤参数**独立填写**。若多步针对同一用户，运营需要在各节点重复填写 `target_handle` 等，系统不会自动从上一节点带入。步骤间传参留到以后，不在本阶段做一半。

`create_post` / `create_story` 仍按契约展示 `file_urls` 等字段，并在节点和发送确认时提示「实打上传尚未打通」。允许保存和发送（便于以后打通后不必改编排），但不得在界面或文档里写成已经能发帖。

**「发令」页本阶段保留，但不扩展成多动作。** 它继续只提交单个 `MANUAL_ACTION`，用于快捷联调和单次操作。多动作必须走「编辑 → 发送」。只含一个节点的定义，经发送页发出后，在追踪和结果上应与「发令」发出的单动作 Signal 同类可比（都是一条 Signal、一种动作、一条 Todo）。

默认假设：本阶段不合并「发令」与「Signal 编辑」，以免打断已经跑通的单动作联调。中期可以再评估把「发令」收成发送页上的「快捷单动作」，但不作为本阶段验收项。长期不得维持两套互相打架的参数口径：发令与编辑器必须共用同一份动作白名单和 params 契约。

## 8. 与 Todo / Behavior 的关系

既有分层不变，也不在产品上另开「直派 Behavior」的暗门：

- Signal 仍然是事实：这里的事实是「运营请求在某台已绑定设备上，按快照执行这一串动作」。
- Todo 仍然是可调度的决策项；Behavior 仍然是一次设备执行，一次 Behavior 对应一个动作。
- 追踪仍按 `signal_id → todo_id → behavior_id` 贯通。
- 重试仍是 Todo 状态机的职责，不发明一种失败 Signal 回灌。
- 设备离线不是失败；`behavior.execute` 对单个动作的信封形状，产品不要求为了多动作去改成「一次 Behavior 带一串动作」。

**默认产品映射（供技术架构师确认，不视为已经实现）：**

一条包含 N 个动作的已发送 Signal，由策略展开为 **N 条有序 Todo**，每条 Todo 对应一个动作、再晋升为一次 Behavior。这与架构里「获客包可产出有序列 Todo」是同一类展开，只是本阶段只做手动 Signal，不改造获客包。前一条 Todo 成功后，才晋升下一条；Behavior 不根据结果临时决定下一步动作。

因此，产品要改变的是「一条 Signal 只生成一种动作、一条 Todo」这条约定，而不是「一次 Behavior 只执行一个动作」。上一轮明确后置的服务端 `executePipeline`（给客户端下发步骤数组、在一次执行里跑完整条链），**不是本阶段的产品前提**。若架构师论证必须走那种形态，需要单独说明它如何满足「每一步在追踪里可独立看到、可按步失败与重试」；默认方案不选它。

单动作旧 payload（`{ "action", "params" }`）必须继续有效，并视为长度为 1 的序列。默认假设：多动作仍使用 Signal 类型 `MANUAL_ACTION` 与 playbook `manual`，把 payload 扩展为有序 `steps`，避免再增加一种事实类型。是否采用该形状由实现方案确认，但对外语义必须与上兼容。

去重是本阶段必须改口径的点。今天按 **Todo 类型（即动作）** 做 `already_open`：同一设备上已有未完成的同类 Todo 时，不再新建一条。多动作序列里允许出现两次相同动作（例如先 `follow_user` A，再 `follow_user` B），也允许与序列外其他 Signal 撞上同类 Todo。默认规则：

- **同一条 Signal 内部**：即使动作类型相同，也不得用「同类未完成」把后一步吞掉或跳过。
- **与其他 Signal 冲突**：晋升到某一步时，若该设备上已有**其他 Signal** 留下的未完成同类 Todo，本步等待对方结束后再晋升，不静默合并，也不取消对方。等待不是失败。

## 9. 失败、中断与重试

失败分类沿用现表，不新增 class：`session` / `platform_risk` / `network` / `script` / `host`。动作内部因跳转而产生的 pending **不是失败**，该步保持执行中，整条链在该步上等待。

| 情况 | 该步 | 后续步骤 | 整条 Signal |
|------|------|----------|-------------|
| 该步成功 | 成功 | 开始下一步 | 全部成功才算成功 |
| 设备离线、或与其他 Signal 的同类 Todo 冲突而等待 | 等待 / pending，不是失败 | 不得开始 | 进行中 |
| 动作内部 pending（跳转后续跑） | 执行中，不是失败 | 不得开始 | 进行中 |
| `network` / `script` / `host`，且该 Todo 策略允许重试 | 按既有 Todo 策略重试；未到终态前不算最终失败 | 不得开始 | 进行中 |
| 该步最终失败（含重试用尽） | 失败 | 取消（原因：前一步失败），不再执行 | 失败 |
| `session` / `platform_risk` | 失败，**不按网络错误自动重试**；需在本机重新登录或处理风控 | 取消，不再执行 | 失败 |
| 运营取消整条 Signal | 当前未完成步骤取消；已成功步骤保持成功 | 未开始的取消 | 取消 |
| 运营对**失败的那一步**发起重试，且随后该步成功 | 该步改为成功（按 Todo 重试） | 从下一步继续串行 | 视后续结果 |

补充规则：

- 本阶段不允许「跳过失败步骤继续」，也不允许对已发送实例改步骤或从中间插入节点。要改编排，应改定义后重新发送（新的实例、新的幂等键）。
- 已成功步骤不做业务回滚（不会自动取关、撤回已发私信或取消已发出的点赞）。产品不承诺补偿动作。
- 运行中的实例不可在编辑页改快照。
- `create_post` / `create_story` 在上传未打通前，live 失败按该步最终失败处理，后续步骤取消，且不得误报成功。

## 10. 验收标准

以下均需在后台（可先用 demo 设备走通交互，再在 live 设备验证串行与失败）可重复验证。demo 路径不得访问 Instagram；live 失败不得回落演示数据。不把尚未打通的发帖成功当作验收通过。

1. 导航中「创建 Signal」已更名为「发送 Signal」，可以打开发送页；旧入口不会丢到空白页。来源事件 `INBOX_ACTIVITY` / `PROFILE_SYNC_NEEDED` 仍能从发送页创建。
2. 「Signal 编辑」可以从动作面板拖拽至少两个不同动作到画布，排成一条单链，为每个节点填写必填参数并保存为带名称的定义。不选设备也能保存。
3. 画布出现分叉、环、孤立节点或空画布时，保存为可发送定义或进入发送会被拒绝，并给出原因。
4. 发送页选择该定义和一台已绑定设备后，能创建一条 Signal 实例；追踪页能看到该 Signal 下按顺序排列的多个步骤，每一步有动作名、状态，而不是只有 UUID。
5. 串行：在前一步未到成功终态前，后一步不得进入执行；前一步成功后，后一步才会开始。可用「第一步选较慢或可观察的动作，第二步是否提前出现执行中」来验证。
6. 失败中止：人为让第一步最终失败（含 live 下使用尚未打通的 `create_post` / `create_story`），第二步不得执行，并显示为因上一步失败而取消；整条 Signal 为失败。
7. 对失败的第一步重试并成功后，第二步才会开始；不提供「跳过第一步继续」。
8. 运营取消一条尚未全部完成的 Signal 后，未完成与未开始的步骤被取消，已成功步骤保持成功。
9. 同一条定义里连续两个相同动作、但参数不同（例如两个 `follow_user` 跟不同 `target_handle`），发送后必须生成两个独立步骤，不得被同类去重吞掉后一步。
10. 「发令」页仍可提交单个 `MANUAL_ACTION`，并走完整追踪；既有单动作 Signal 仍能被理解和展示。不得要求运营为了发一个 `sync_profile` 先去画流程图。
11. 编辑器与发令都不得出现 `send_reply`，都不得把 Cookie / `sessionid` 做成表单字段。
12. 含 `create_post` 或 `create_story` 的定义可以保存，但节点和发送确认有「实打上传尚未打通」的说明；live 不得把失败显示成发帖成功。
13. 离线设备允许发送，对应步骤保持等待，不把离线写成失败。
14. 保存定义后修改节点参数，只影响之后新发送的实例，已发出的实例步骤与参数不变。

## 11. 假设与未决

下列默认假设已按「先给口径、再往下写」处理。实现方案或评审若要改其中任何一条，需要明示，不要 silently 改语义。

已采纳的默认假设：

1. 定义与实例分离；设备只在发送时选择。
2. 本阶段只做单链串行，不做并行、条件、循环、延时节点和步骤间传参。
3. 「发令」页保留为单动作快捷入口，不在本阶段合并或撤掉。
4. 一条 N 步 Signal 展开为 N 条有序 Todo、N 次单动作 Behavior；不以客户端 `executePipeline` 为产品前提。
5. Signal 类型继续用 `MANUAL_ACTION`，旧的单动作 payload 视为 1 步；多动作用有序步骤扩展 payload（具体字段名由实现方案定）。
6. 序列内部不去重吞步骤；与其他 Signal 的同类未完成 Todo 冲突时等待，不合并、不互相取消。
7. 失败即停止后续步骤（后续为取消）；允许对失败步重试，不允许跳过；已成功步骤不回滚。
8. `create_post` / `create_story` 可编排、可发送，但不表示上传已打通。

仍待确认（不挡住把本文当作本阶段产品口径，但实现前最好拍板）：

1. Signal 定义是否需要「启用 / 停用」或简单权限（默认：只有后台登录者可编辑和发送，定义没有更细的角色模型）。
2. 发送页是否允许在发出前对快照做一次只读确认页上的最终改参数（默认：发送前可改本次快照参数，但不写回定义，除非运营明确点「写回定义」；若实现成本高，可先做「完全按定义发送，要改先回编辑页」）。
3. 与其他 Signal 同类 Todo 冲突时，是「等待」还是「该步失败并中止本序列」。默认是等待。若等待可能拖死一条链，实现方案需给出可观察的等待状态，而不是看起来像卡住。
4. 是否提供「复制已发送实例为新定义」。默认：本阶段可做「从定义另存」，不做从实例反向生成定义，除非实现很顺手。
5. 追踪页要改到什么深度。本阶段最低要求见验收第 4 条；完整时间线和每步结果摘要希望尽量有，但不要求重写整页。
6. 定义的删除规则。默认：已被实例引用的定义可以删除或归档，已发出的实例及其快照仍保留，追踪不受影响。
