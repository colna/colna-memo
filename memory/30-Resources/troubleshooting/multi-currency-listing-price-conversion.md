# 多币种挂牌价手工折 CNY → 币种串档

## 症状

一份「平台报价梯」报告里，同一条需求的价格比真实值大 **70–80 倍**，且不是一处：

- ₹12,500–37,500 被当成 $12,500–37,500 → 该帖从「¥8 万级」落到实际 **¥881–2,643**
- ₹1,500–12,500 被当成 $ → 实际 **¥106–881**，该帖从 ¥3,000 档掉到 ¥493 档
- 「中位价区间 ¥33–¥167,101」：¥167,101 是**误把某条 `budget_max` 当区间上界**，实际 **¥24–¥15,039**
- 由上述推出的结论「这个市场试错很贵」因此整段作废（真实情况是投标免费，只是每月 6 标）

## 根因

1. **源头字段拆开了**：原始 API 每条都有 `currency` + `budget_min` + `budget_max`，但汇总时把金额抽成裸数字，**币种丢了**（USD 40 / INR 28 / AUD 4 / EUR 4 / GBP 2 / NZD 1 混在一列）。
2. **手工换汇**：人眼逐条换算，遇到 ₹ / $ 混排时按「看起来像美元」的直觉处理，错了不会报错，只会静默变小/变大。
3. **只有单点核对**：`grep` 抽查几条对得上就发布，没做**逐条**比对；单条抽查对不出「币种错了」。

## 修法（落成了两道闸）

1. **折算交给脚本，人不再算**：`tiers.py` 只读 CSV，用 `currency` 字段选汇率（USD 6.684036；INR 由同批数据反推 0.070481），输出四档/分组/零模型，`--json` 供比对。报告里的每个金额都必须来自这个脚本的输出。
2. **校验按 `(currency, budget_min, budget_max)` 逐条回算**：`verify_addendum.py` 取报告引用的每条帖，用原币区间 × 反推汇率算 CNY 区间，与报告写的数比（±2%）；**币种串档直接 FAIL**。本轮就是这样抓出 AUD 那条（AUD 30–250 → ¥652，曾被写成 $）。

## 可迁移的两条

- **任何「汇总表把单位抽掉」的聚合都是坑源**：金额必带币种、时间必带时区、比例必带分母。抽成裸数就一定会有人按错口径累加。
- **多币种场景的最小校验 = 逐条回算**，不是抽查。抽查只证明「样例对」，逐条才证明「没有串档」。
- 相关：区间上下界别混用——`budget_max` 是**单条的上界**，不是**样本区间的上界**；写「中位价区间」应该用 `median(mid_price)` 的 min/max。
