# 查证纪律

2026-07-18 一天内「没查证就下结论」犯了 3 次，07-20 又犯第 4 次 —— **而且第 4 次就发生在我刚写下「这次是先查证再下结论的正面例子」之后**。这篇是把这些教训固化成可执行的检查动作。

## ⭐⭐ 核心：断言涉及控制流，就必须验证控制流本身

**07-20 的翻车（最典型）**：

我断言「取消 / 未接通的通话没有结算弹窗，所以 `CALL_SETTLED` 紧跟 navigate 就发了，反而比 RECORDED 更早」。
还基于这个认知把设计从「只认 CALL_SETTLED」改成「两个信号凑齐才跳」，并把这句话写进了代码注释和 commit message。

**CR 一查：那条路径压根不发这个事件。** 取消走 `handleOutgoingFailure`，只 emit `CALL_OUTGOING_ENDED`，
而 `CALL_SETTLED` 唯一的 emit 点在 `handleCallEnded` 里。我的「修复」让这条路径从「可能不跳」变成了**必定不跳**。

**我当时确实读了文件** —— 读的是 `handleCallEnded` 里的弹窗序列，看到弹窗是 `await` 的、看到 emit 在最后。
但断言涉及的是**另一条路径是否流经该函数**，这是**不同的问题**。我用前者的证据支撑了后者的结论，
还因此产生了「我已经查证过了」的虚假信心 —— 这比根本没查更危险。

> **动作**：断言「某事件在某路径会 / 不会触发」时，必须
> ① `grep` 出该事件的**全部 emit 点** → ② 逐条确认目标路径是否流经。
> **这是 30 秒的事**，读一眼目标函数内部实现不算数。

## 四次同类错误的共同点

| # | 错误 | 真相 |
|---|---|---|
| 1 | 用户报「切不动会话」，我立刻怀疑自己刚加的改动，分析出一条严丝合缝的死锁链就回滚了 | 回滚后现象依旧。根因是后端。**我那条死锁链分析本身没错、也确实是隐患，但不是这次的根因** |
| 2 | 用户问 `centsPerMinute: 0`，我说「更可能是数据侧问题」 | CR 查出是**取值路径 bug**（少个 `\|\|` 兜底），资损 P1 |
| 3 | 注释里写「`startAVCall` 的 `maxDurationMs` 由端上定时挂断兜底」 | 读端仓：`startAVCall` **只读 userId/type/orderId**，全端仓 grep `maxDurationMs` 零命中。**更打脸的是本仓既有注释就写着实情，我连眼前的注释都没读** |
| 4 | 「取消路径 CALL_SETTLED 更早」（见上） | 那条路径不发这个事件 |

**共同点：推断了控制流 / 外部行为，却没去读控制流 / 外部实现。**

- 「传了参数」≠「对方会用」（#3）
- 「事件存在」≠「这条路径会发」（#4）
- 「现象出现在某次改动之后」≠「由它导致」（#1）
- 「看起来像数据问题」≠「不是代码问题」（#2）

**纠正**：涉及端能力的判断，`GraceChat-Earn-Android` / `Kira-Android` 端仓就在同一工作区，**直接读端仓源码**，
不要靠调用侧代码反推。

## 排查纪律：先让失败说话，再谈修法

**07-18 的两版错误方向**：消息刷新后缺一段，我先后改了「加卸载兜底 flush」「防抖改节流」——
改的都是「**什么时候写**」，而真相是「**根本写不进去**」（IndexedDB `DataCloneError`）。

**转折点是给静默的 `catch` 加了一行日志。**

> **一个吞掉异常的 catch，能让人朝错误方向修无数遍。**
> 排查时优先把「静默失败」暴露出来，再谈修法。

配套的收敛姿势（每一步都用日志排除一类可能，而不是猜）：

```
稳定复现（每次都 37 条）  → 排除随机丢失
afterTtl == onDisk        → 排除 TTL
queued(45) != onDisk(37)  → 锁定「写不进」而非「读丢失」
catch 加日志拿到 error.name → 定案
```

## 代码 review：diff 视角与全量视角互补，不能互相替代

07-20 review sitin4.0 时先做全量、后做 `git diff feature/pwa...feature/sitin4.0`，两者抓到的问题**几乎不重叠**：

| 视角 | 能看见 | 看不见 |
|---|---|---|
| **全量**（对照文档审现有代码） | 「现在的代码对不对」—— **缺失型**问题：字段定义了零调用、下发了不消费、文档要求但没写 | 已被删除的代码 |
| **diff**（审这次改动干了什么） | 整体删除留下的**语义孤儿**、功能是「丢了」还是「有意搬家」、**老用户回归** | 没改动的地方 |

**只有 diff 能发现的实例**：4.0 删了两个页面（~2950 行），`tsc` 全绿没断 import，但
`aiPersonaMessageStore` 消费方归零、对应接口再无调用方，而 **WS handler 仍在 `init()`、还在往没人读的 store 写**。
全量 review 看到的是「这些文件都在、看起来正常」。

**只有全量能发现的实例**：`setSuppressed` 零调用、`isProcessing` 死代码、`reason` 字段下发了不消费 ——
这些地方**本次没改动**，不在 diff 里。

## 设计原则：「推断」和「查询」有得选时，永远选查询

**实例**：判断「会话的任务是否已完成」，本来靠「服务端本轮返回的列表里没有它 = 已完成」推断。
这个推断的隐含前提是「返回的是全量」—— 而 proto 里 `limit` 不传时默认只有 20。被截断的会话会被误判成「任务已完成」，
**卡片凭空消失、会话锁被误解开**。

改成对缺席的会话逐个调单会话查询接口（返回权威），推断变查询。

> 缺席、超时、没返回 —— 这类**「以沉默为依据」的判断**，前提往往是个没人验证过的隐含约定。

## 设计原则：问「出错的方向是什么」，而不只是「会不会出错」

同一个功能的两种实现，出错方向决定了它有多可怕：

| 实现 | 出错时 | 谁会发现 |
|---|---|---|
| 缺席即清空 | **误清** → 卡片消失、任务被当作已完成 | **没人**（静默数据损坏） |
| 缺席则查询 | 查询失败 → 维持现状（锁着） | 用户（切不了会话，症状明显） |

> **让失败模式朝着「用户能看见」的方向倒。** 可见的功能阻塞远好过静默的数据损坏。

## 加防御之前，先查证威胁是否真实

差点为「缺席会话逐个查询」加一个每轮请求数上限，怕请求风暴。
去查 `partialize` 才发现 `tasks` 根本不落盘（注释写着「避免冷启动复活隔夜任务」）—— **风暴场景不存在**。

按 CLAUDE.md「不为永远不会发生的场景写 fallback」，这个上限该砍。

## 检查清单

下结论前问自己：

- [ ] 这个断言涉及**控制流**吗？→ grep 出全部触发点，逐条确认路径是否流经
- [ ] 涉及**外部系统 / 端能力**吗？→ 直接读对方源码，别从调用侧反推
- [ ] 涉及**接口语义**（全量？增量？有没有 limit？）→ 读 proto / 文档原文，别信口头确认
- [ ] 涉及**单位换算**？→ 用一组真实值端到端算一遍
- [ ] 我读的文件，**真的在回答我这个问题**吗？还是在回答一个相邻的问题？

## 2026-07-23 补：验证「跑通了」时的三个新坑

这轮做 PWA 语音输入手势，验证方法本身出错三次，**每次断言、脚本、结论都没写错，错在别的地方**。

### ⭐⭐ 1. 选了一条不会触发问题的路径，然后宣布通过

需求：「开始录音不要震动」。我删掉 `startRecording` 里的震动，测「按住 600ms 不松手」得到 `[]`，判定通过。

**但轻点才是用户开始录音的主要方式** —— 它走另一个分支（`goHandsFree`）照样震。需求实际没满足，是后来 self-review 才发现的。

> **验证要覆盖「用户实际最常走的那条路径」，不是最好测的那条。** 一个功能有几条入口，就要逐条测；只测其中一条得到期望值，证明不了需求满足。修完后我改成四条路径全测，输出成一张表。

### ⭐⭐ 2. 只看结果，分不清两种不同的原因

验「第二根手指会不会误发第一根的录音」，结果是「录音条消失了」—— 我当成修复失败。

实际是**测试脚本传错了参数**（CDP `Input.dispatchTouchEvent` 的 `touchEnd` 里 `touchPoints` 是**被抬起的点**，不是剩余的点），抬起的其实是第一根手指，那次发送完全正确。

救回来的是**事件轨迹**：打了 `pointerdown#2 → pointerdown#3 → pointerup#2`，一眼看出抬的是 #2。

> 「录音没了」可能是误发、正确发送、被取消——**结果相同、原因不同**。排查手势 / 事件驱动的问题，先把事件流（含 id）打出来再下结论，不要从终态倒推原因。

### ⭐ 3. 探针自己有 bug，输出是假象

用 `navigator.vibrate` 劫持记录震动序列，每个用例前重置。但**重置代码每次都在已包装过的函数外面再包一层**，第 N 个用例的每次调用就记 N 遍，输出成了 `[[10,30,10],[10,30,10]]`、`[10,10,10]`。

差点当成「真的重复触发」去查代码。

> **工具的输出也要怀疑。** 出现「重复」「翻倍」「数量对不上」这类规律性异常时，先怀疑测量装置，再怀疑被测对象。包装类探针要做幂等（`if (!window.__wrapped)`）。

### ⭐ 4. 断言要读计算值，不要读自己写进去的值

给波形加「拖进垃圾桶时淡出」，代码里写了 `opacity: armed ? 0 : 1`，但 `getComputedStyle` 读出来是 `1` ——
入场那条 `animation-fill-mode: both` 的填充值**优先级高于内联样式**，把它盖住了。

> 读自己写进去的值只能证明代码跑到了，证明不了它生效。视觉相关的断言一律读 `getComputedStyle`。

### ⭐ 5. 数值断言全绿，不等于视觉正确

锁的悬浮球坐标、阈值、跟手比例全部符合预期，但它被拎起来后**压在提示条上** —— 重叠不在任何一条断言的覆盖范围内。

> 凡是新增浮层 / 改变元素位置，除数值断言外**必须看一眼截图**。
