# RN 列表/卡组共享一个池：入口游标与「不可再操作项」

出处：sitin-rn `apps/luka` 的 Nearby（大卡＝划卡组、小卡＝瀑布流），2026-09-21 用户报障。
两个视图共享同一个候选池，列表打招呼后卡面保留 `Sent` 状态（不把人从池里移除）。

## 症状

列表里把人全打招呼后切回卡组：卡组停在刚打过招呼的人上，不能再打招呼、也划不走
（照片区只刮不划），只能点 Skip。预期应落到未打招呼的人。

## 两个根因

1. **入口索引只在挂载那一帧生效。** 卡组的 `initialIndex` 是 React 挂载时的
   `useState` 初值，之后数据追加不会重新应用。而「跳过已发集合」的扫描函数在
   **游标之后整段都发过招呼**时回落到游标本身（一个 `Sent` 卡）——补批的新人是在
   挂载**之后**才到的，没有任何东西把游标往前推，于是永远停在那一张。
2. **不可再操作的项目仍保留「首次操作门」。** 划卡的门是「未刮开只有信息带能划，
   刮开整卡能划」，Sent 卡沿用同一道门 → 用户读成卡死。

## 修法（可复用的三条）

- 扫描函数**区分「找到」与「没有」**：返回 `number | null`，`null` 表示没有能停的项；
  不要用「回落到调用方给的起点」冒充结果，调用方会把不可停的项当入口。
- 卡组视图在「没有能停的项」时：停在游标（不空屏）+ **主动补一批**，补到有人可停或
  确实没有下一页为止；批数据落进池子后，用一个命令式 `skipTo(index)` 把游标一步推
  过去（吸附、无动画、不上报）。命令式方法要和「删卡重排」用同一套善后：游标、两个
  槽的位移归零、展示上报与预取续接。
- 推游标只在**数据追加**时做，不要监听「跳过集合变化」：用户刚点了打招呼时集合会变，
  而那张卡此刻正等飞行动画/定时前进，抢跑会多跳一张（本次加了「该卡打招呼在飞」的
  闩）。另外只在当前项确实不可停时才推，别把用户正在看的卡抽走。
- UI 门要跟着业务能力走：不可能再操作的项（Sent）直接放开操作门（整卡可划），
  别让「不能操作」叠上「划不动」。

## 验证方式

纯函数（`firstUnsentNearbyIndex` / `deckSkipTargetAfterAppend`）单测覆盖「整段已发 →
null / 补批吸附」；容器侧没有渲染测试，靠 typecheck + biome + Metro bundle 200 检查
编译，实机走查留真机。
