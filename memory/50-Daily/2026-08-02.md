## 工作日志 — 21:22 colna 检索优化 + 修全量重建致命 bug + 换 e5-base

- **做了什么**:按「检索优化方案」改 colna(`colna-memo/src`),四处:
  1. **修全量重建致命 bug(根因)**:`store.rs` 的 `insert_chunks`/`upsert_chunks` 一次性写入全部块,但 **zvec 单次写入上限 1024 条**,1367 块 → `Too many docs: 1367 exceeds max write batch size of 1024` → 索引写不成、空索引、检索 0 结果。**之前 N 次全量重建/`colna sync` 首次全量失败全是这个**(旧 2.4G 索引是增量一点点攒的才没触发)。修法:分批写入(每批 512)。
  2. **上下文增强切块**(精准度):`chunker.rs` 给 `Chunk` 加 `embed_text`,维护标题层级栈算「面包屑」,**嵌入文本 = 文档标题 · 日期 · 面包屑 + 正文**;展示/FTS/存储仍用原 `text`。块 ID 不变(`source_path+heading+序号`)。`main.rs` 两处嵌入改用 `embed_text`。
  3. **换模型 e5-small → e5-base**(精准度):`embedder.rs` `MultilingualE5Small→Base`、`DIM 384→768`。
  4. **嵌入分批 32**(效率/内存):`embedder.rs` `embed(..., Some(32))`,共享机器 swap 吃紧时避免大批次抖动拖慢。
- **效率项**:编译 release 版(`COLNA_PROFILE=release`,`./colna` wrapper 已支持),嵌入/检索快数倍。
- **结果**:全量重建成功「写入 1367 块」,**索引 2.4G → 13M**,检索恢复且结果带面包屑上下文;`colna sync` 收尾成功。重建用时 ~7.5 分钟(嵌入多核 844% CPU)。
- **踩坑(关键沉淀)**:① zvec 写入硬上限 1024,任何一次 insert/upsert 都要分批;② 全量重建卡死/爆内存的表象(另一 agent 报 29GB swap)其实是被 1024 报错前的嵌入 + 机器本身 swap 吃紧叠加误导,真凶是写入超限;③ 本环境后台任务(nohup/setsid 都试过)会在会话空档被连进程组杀,长任务要**前台阻塞**跑。
- **待办**:`src/{chunker,embedder,main,store}.rs` 4 个改动**未 commit**(规范模式等用户批准);尤其分批写入是真 bugfix,建议提交。
