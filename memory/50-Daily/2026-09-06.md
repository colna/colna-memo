## 工作日志 — 23:05 koda 聊天输入框升降卡顿:memo 化 composer 子树

- **做了什么**:抽 list 后用户反馈「输入框上升下落时还是卡顿」。在 `chat/[id].tsx` 用 `useMemo` 把 `KeyboardStickyView` 里整块 composer 子树(billing banner + KodaExchangeChips + ChatInputBar + ChatActionBar)缓存成一个 element,**依赖数组刻意不含 `keyboardInset`**;JSX 改为 `<KeyboardStickyView>{composer}</KeyboardStickyView>`。commit `af3166c3`。
- **为什么**:对比 iris,iris 的 `KeyboardStickyView` **只包一个 `ChatInputBar`**(轻子树);koda 因产品要求把工具栏也塞进去随键盘 transform,子树大得多。而每次键盘开合触发 `setKeyboardInset` → 屏幕 re-render → 重建含 `TextInput` 的整块 composer,正好和 transform 动画抢帧 → 升降掉帧。两个 bar 都不是 `memo`(iris 的 ChatInputBar 也不是,但它靠子树小 + 重渲染便宜扛住)。memo 化 element 后,keyboardInset 变化时 React 拿到同一引用直接 bail out 整个子树,transform 独占动画。
- **结果**:biome / koda typecheck / boundaries 全过。已 push `feat/koda-ce`(PR #394)。**根因判断:消除「re-render × transform 抢帧」这条最可能路径;若真机仍卡,剩余嫌疑是 transform 大子树本身的合成开销(ChatActionBar 必须跟随、无法瘦身)。原生动画本地测不出,需 EAS 真机验证。**
- **沉淀**:RN「随键盘 transform 的容器卡顿」排查 —— 除上面列表四步外,还要看:⑤ **KeyboardStickyView/被 transform 的子树是否会因无关 state(如 keyboardInset)re-render**;若会,用 `useMemo` 缓存该子树 element、把无关 state 排除出依赖,让动画独占帧。⑥ 子树尽量小(iris 只 transform 输入框本身)。
