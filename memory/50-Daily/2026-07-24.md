## 工作日志 — 14:40 browser-replay 修「Instagram DM 录制回放失败」

用户拿一份 Instagram DM 的真实录制(10 步)报「输入步骤失败」,回放第 6 步报「页面上找不到该元素。已尝试：」(尝试列表为空)。查下来是**三个独立缺陷叠加**,已全部修掉并补回归测试。

**诊断**(先只读 JSON + 截图就定位到了)
1. 第 6 步 = `key` Enter,`selector: null`、`selectorFallbacks: []` —— 候选归零 → resolve 永远拿不到元素 → 等满 10s → `diagnose()` 遍历空数组,所以「已尝试：」后面是空的。
2. 根因:`push('structural', ...)` 默认走唯一性校验,Instagram 每层单子节点 → `nthOfType` 退化成裸 div → 12 层封顶后匹配上千个 → 被丢弃。注释写「一定能生成，作为保底」,与实现矛盾。
3. 更严重:整份录制**没有任何 input 步骤**,"hello" 没录进来。用户确认是**现场敲进去的** → 录制器漏录,不是操作问题。

**改动**(`browser-replay`)
- `selector.js`:新增 `nthChild()`;结构路径不唯一时退到逐层 `:nth-child`(封顶 12→30);两条都不唯一且别无候选时无条件塞一条(score 20);`push` 改为返回 boolean。
- `content.js`:新增 `editingHostOf()` 把待结算目标归一到 contenteditable 宿主(Lexical 重建内部节点导致旧节点脱离文档、读不到值);contenteditable 上打字时 keydown 也 `markPendingInput`;`key`/`keystroke` 定位不到**或只靠弱候选(score<55)命中**时退到 `document.activeElement`;零候选时超时从 10s 降到 2s。
- `executor.js`:`typeIntoEditable` 在合成 beforeinput 没人接管后,先逐键敲一遍再退到直写 textContent。

**验证**:`node test/run-all.mjs` 全绿(selector 16/16 + e2e 全过)。新增 harness fixture 复刻 Instagram 三重形态(14 层无标识 div 汤×2 条同构链 + window 捕获阶段吞掉输入事件 + 每次输入重建内部 `<p>`),e2e 断言:靠 keydown 录到输入、无零候选步骤、按键退到 activeElement、回放发出的不是空消息。selector 单测加「深层无标识节点不会候选归零」。

**踩坑**:第 2 条修复(非唯一保底)会**和第 3 条(activeElement 兜底)打架** —— 有候选就命中错元素,兜底反而不触发。所以规则定成「强候选才信任,弱命中让位焦点」。另:e2e fixture 里 contenteditable 默认高度 0 且在视口外,realClick 取中心点会点到别的元素,要给尺寸 + 先 scrollIntoView。

## 工作日志 — 16:20 browser-replay 修「草稿被当基线而漏录输入」(附一次误诊订正)

用户复验:选择器改进生效(9 步里 7 步语义候选,编辑区拿到 `div[aria-placeholder="发消息..."]` 74 分、发送按钮 `div[aria-label="发送"]` 80 分),**但输入仍然没录到**。

**⭐ 我先误诊了一轮**:看到这份录制里连 `key` 步骤都没有(用户点的发送而非回车),就推断「IG 把 keydown 也吃掉了」,动手加了 MutationObserver 兜底。**证据不支持** —— 上一份录制里 `key` Enter 步骤明明录到了,恰恰证明 keydown 通道是通的。已把 MutationObserver 撤掉,不留基于错误假设的代码。

**真因**:`onFocusIn` 里 `recordedValues.set(el, readValue(el))` 把聚焦那刻的内容存为基线。IG **会恢复草稿**,「666」在聚焦前就已在框里 → blur 结算时 `值没变` → 静默跳过 → 脚本里一条 input 都没有 → 回放在空框上点发送,**且每步都显示成功**。

这个解释同时对上两份录制的所有细节,包括「时间线里找不到任何打字空档」(index 4→5 只隔 1ms)—— 因为录制期间用户确实没打字。

**修法**:`recordedValues.set(el, el.isContentEditable ? '' : readValue(el))`。自绘编辑器不吃基线(编辑区内容就是要被发出去的东西,不管谁放进去的);表单字段保持原样(预填值多,Tab 扫过不该产出一堆步骤)。

**验证**:harness 的 IG 编辑器补了发送按钮 + `seedIgDraft()`,新增 e2e 场景断言「聚焦前就存在的内容也被录进来」「空编辑区回放也发得出同样的消息」。`run-all` 全绿(16/16 + e2e)。commit `7d508db`。

**教训**:定位到「某步没产出」时,要先分清是**没观测到**还是**观测到了但被判定为无需记录**。我一路在查前者(事件通道),真因在后者(去重基线)。两者的症状完全一样,但排查方向相反 —— 先看有没有「静默跳过」的分支,比猜哪条事件通道被掐了更快。

## 工作日志 — 17:10 browser-replay 修「回放误触发录音」+ 导出加版本标记

用户第三次复验:选择器质量已达标,但输入仍没录到,且**回放触发了录音**。

**⭐ 误触发录音的成因**(能从导出 JSON 直接复原):IG 在输入框为空时把**发送按钮原地换成麦克风**,位置一模一样。语义候选 `div[aria-label="发送"]` 匹配不上 → 退到结构路径 → 按位置命中麦克风 → 点下去开始录音。

我的 `looksLikeTarget` **本来认出了**这不是发送按钮(aria-label 对不上),但上一版我多写了一层「都不像就退回不校验的第一个匹配」,理由是「校验只是排序偏好,不该把有点东西变成什么都没有」——**这个取舍是错的**。已去掉,弱候选的校验现在是硬性的。

> ⭐ 原则:**「找不到」和「找错了」不是同一量级的失败**。找不到只是这一步停下;找错了是**执行了另一个动作**(开始录音 / 点了别的按钮 / 提交了别的表单),而且每步都显示成功。给兜底加「宁可命中点什么」的退路时,要先问一句:命中错的会发生什么?

**输入仍没录到 = 页面里跑的是旧 content script**。逐行走过代码可证:`onFocusIn` 现在对 contenteditable 把基线设为 `''`,blur 时 `"777" ≠ ''` 必然产出 input;`recordedValues` 全项目只有两处写入,没有第三条路径。→ MV3 改 content script 必须**两步**:`chrome://extensions` 点刷新 ↻ **且**重新加载目标标签页(已打开页面里的旧 content script 不会自动替换)。

**据此加了防呆**:导出 JSON 增加 `extVersion`(取自 manifest),版本 0.1.0 → 0.2.0。以后收到录制先看这个字段,不用再靠推理判断代码是否生效 —— 这一轮就因为这个白排查了一次。
