## 工作日志 — HH:xx snapchat DM 监听跨 reload 去重(止未读反复上报)

- **现象**:orderKey 修好后 getChatMessages 对建斌历正确返回 0(旧内容全过滤),但 NEW_MESSAGE 仍一直上报。
- **根因**:getChatMessages 后端派 navigateToInbox **整页 reload** → 监听重启「首次扫描」→ 内存快照丢 →
  同一条未读(没打开的「新的 Snap」一直不清)每次 reload 都被当"新"重报 → 服务端反复下发 getChatMessages 空转。
- **修**(startDMListener.js):用 **sessionStorage** 持久化「已报未读 chatId→status|timestamp」(同源刷新保留),
  diffAndReport 只报 `reported[chatId] != status|timestamp` 的未读,同一条不再重报,直到 timestamp/status 变。
  统一了首次扫描/后续扫描的上报门(都走持久化 gate)。上线 v110。
- 关联:与 fiber orderKey 修复(v105/v118)一起,基本闭环「一直下发 getChatMessages / 通话 churn」。
- 教训:注入脚本靠内存做跨请求去重会被整页 reload 清掉;需要跨 reload 的状态用 sessionStorage(同源保留)。
