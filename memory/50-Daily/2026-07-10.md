## 工作日志 — 通话入口透传 + video tips 通话 60s 上限

**分支** `personal/zz/pwa-outgoing-call-native`（叠在 PR #584 上；用户要求「先做第一个，就在当前分支做」）

**需求**（飞书 `wiki/MCpwwzZvviKByjk7kBhczdPVnzf`）：chat 红色态 video tips 卡片发起的通话，**1min 时结束通话，主动挂断不给钱**。本次只做前半：入口透传 + 60 秒自动挂断。后半（倒计时 UI、主动挂断不给钱）待产品/后端确认归属，未做。

**为什么新加 `entry` 而不是扩 `source`**
`ConnectSession.source` 已被 `handleCallBegin` 和埋点依赖：**任何**主叫都是 `source: "active_call"`，不区分按钮。所以 `source` = 通话怎么来的，`entry` = 从哪个界面打的，两者正交。

**改动**
| 文件 | 改了什么 |
|---|---|
| `src/types/call.ts` | 新增 `export type CallEntry = "video_tips" \| "debug"`；`ConnectSession` 加 `entry?: CallEntry` |
| `src/services/webCallManager.tsx` | `startCall(remoteUserId, callType, entry?)`，把 `entry` 写进 `connectSession` |
| `src/pages/Chat/index.tsx` | `CALL_OUTGOING_START` 带 `entry: "video_tips"` |
| `src/pages/Debug/index.tsx` | 带 `entry: "debug"` |
| `src/hooks/useWebCall.tsx` | `VIDEO_TIPS_CALL_LIMIT_MS = 60_000`；`callLimitTimerRef` / `clearCallLimit()` / `startCallLimit(entry)`；`handleOutgoingStart` 透传 `entry` |

**两个关键决策(坑)**

1. **计时从「接通」起，不从「拨号」起** —— `startCallLimit(session.entry)` 挂在 `handleCallBegin` 里，不在 `handleOutgoingStart`。响铃 30s 没人接不该吃掉这一分钟。
2. **用 `WebCallManager.hangup()` 挂断，不 emit `CALL_USER_HANGUP`** —— 后者的 handler 会置 `isUserHangup = true`，而规格里「打满一分钟」要给钱、「主动挂断」不给钱。走事件等于把自动挂断误判成主动挂断，钱就没了。

**清理点**（`useWebCall` 挂在 App 根，永不卸载，ref 跨通话存活 —— 和 PR #584 的 `isEnded` 泄漏同一个根因）：
`handleCallEnded` 的**两条分支**（有 session / 无 session）各加一次 `clearCallLimit()`，`startCallLimit` 自身入口先 clear 一次，卸载 effect 也补一次。

**踩坑**:两处 `useCallback` 的 deps 数组字面量完全相同(`[reportCallEnd, stopVibration]`),分别属于 `handleCallDecline` 和 `handleCallEnded`。脚本按首次匹配替换,`clearCallLimit` 加错到了 `handleCallDecline` 上。**同名 deps 数组不能靠首次匹配定位**,得用 `rindex` 或先锚定函数名。

**已知缺口(未修)**:APK 内走 native `startAVCall` 提前 return,不经过 `WebCallManager`,`connectSession` 从不填充 → **一分钟上限在 App 内不生效**,需要端上支持。已在 PR #585 描述里挂着这个问题。
