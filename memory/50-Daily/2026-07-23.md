### 01:00 录音条入场动画（commit `188637345`，并入 PR #699）

**需求**：点击开始录音时要有动画，计时和发送箭头自左向右滑入，**弥补 media 请求时间**。

用户点出了一个我没意识到的体验问题：`startRecording` 是**先 `setRecordingNow(true)` 亮出录音条、再 `await start()` 开麦克风**（这个顺序本身是对的，让 UI 立刻响应）。但 `getUserMedia` 那几百毫秒里，录音条已经在了、计时却停在 `0:00`、波形是平的 —— 看着像卡死。

**做法**：计时与发送箭头 `translateX(-14px) + opacity 0` → 归位，`380ms cubic-bezier(.16,1,.3,1)`；箭头再晚 `60ms` 起步，滑入有先后而不是整块平移。动画放完时麦克风通常已开好。

**⭐ `animation-fill-mode: both` 是必须的** —— 少了它首帧会先闪一下终态再跳回起点，反而更难看。

**验证**：点击后 **90ms** 抓中间态（不是只看终态）——计时 `opacity .85 / translateX -2.15px`，箭头 `opacity .53 / translateX -6.57px`，箭头明显落后，证明动画在跑且 60ms 错峰生效；3.3s 后两者都 `opacity 1 / translateX(0)`。截图已发用户。

> 沉淀：**验动画不能只截终态**，那和没动画看起来一模一样。要在动画进行中的某个时刻读 `getComputedStyle` 的 `animationName` / `opacity` / `transform`，才证明得了它真的在动、且参数（时长、延迟、错峰）符合预期。

### 01:32 录音条入场编排重做，逐帧采样揪出两个 bug（commit `7e0628033`，并入 PR #699）

**需求**：动画要从最左侧（垃圾桶旁）滑到最右侧；到位后波形才出现；波形不能一开始就是一条线，要自左向右滚。

**做法**：三段编排。滑行距离**不写死，取波形槽的实测宽度** —— 槽在滑行期间是空的，把「计时 + 箭头」整组左移一个槽宽，正好落在红点右边。波形改为**只渲染已采到的格子、不补基线**，满 30 格后最旧的从左挤掉，自然成为滚动波形。录音条拆成独立组件，入场状态随每次录音重新挂载复位。

**⭐ 最大的收获：验动画不能隔着 CDP 打时间点**

第一版用 `await sleep(16)` + `Runtime.evaluate` 读 transform，测出来标称 16ms、**实际已过约 195ms**（往返延迟把时间轴整个污染了），据此还差点误判缓动没问题。改成**在页面内 `requestAnimationFrame` 连续采样、一次性返回数组**，时间轴才干净。

换了采样方式后立刻暴露两个 bug：

1. **⚠️ `onRecordingChange` 走 passive effect → 滑行行程缩水 210px→60px**
   宿主要据此隐藏两侧按钮，而 effect 在**绘制之后**才跑 —— 录音条第一次布局时那三个按钮还占着位，`useLayoutEffect` 量到的槽宽只有 60px。改为与自身 `setState` **同批**通知。肉眼只觉得「滑得有点短」，逐帧采样才看出起点不对。
2. **⚠️ 卸载时没把录音态收回 `false`** → 宿主两侧按钮永久隐藏，切文字输入即复现。是我上一版加「录音时隐藏按钮」时引入的。

**⭐ 缓动坑**：`cubic-bezier(.16,1,.3,1)`（弹簧式）**在头 10% 时间里走完约 78% 距离** —— 滑行 150ms 就肉眼结束，后面 270ms 空等，正好废掉「用滑行盖住开麦等待」的目的。改用 easeOutQuad `cubic-bezier(.25,.46,.45,.94)`。

**验证**（页面内逐帧）：起点 `-210px`（整个槽宽）→ 平滑铺满全程 → 到位 `461ms` → 波形 `496ms` 出现 → 根数 5→10→25 持续滚入。四阶段截图已发用户。

**残留**
- [ ] 真机未验：滑行 420ms 是估的，若 `getUserMedia` 更慢（首次授权、低端机），动画放完条还是静的
- [ ] 震动反馈仍未真机验证

### 01:52 波形铺满整槽（commit `d48f47b79`，并入 PR #699）

**需求**：用户发参考图 —— 波形间距和大小要改，**要占满，而不是只有一半**。

**根因**：照搬了原型的 `BARS=30`。30 根 × (2.5px 条 + 2px 间距) = **135px**，而槽宽 210px —— 只铺满六成。原型是 366px 宽的固定画板，我们是真实机型，宽度对不上，**照抄写死的根数必然不对**。

**改法**：条宽 2px / 间距 2px / 全圆角，根数改为 `floor((槽宽 + 间距) / (条宽 + 间距))`，用 RecordingBar 已经量到的槽宽算 —— 390px 机型约 53 根，换机型自动适配。

**⭐ 连带发现：采样间隔决定「铺满要多久」**。条数从 30 提到 53 后，原来的 90ms 采样要 **4.8s** 才铺满一行，久到看不出是在滚动。改成 50ms → 约 2.5s。`levels` 窗口从 32 提到 128。**改前先确认了 `VoiceTaskDrawer` 虽然也用 `useVoiceRecorder`、但只取 `durationMs` 不读 `levels`**，不受影响。

**验证**（页面内逐帧）：`513ms` 9 根 16% → `1513ms` 29 根 54% → `2346ms` 46 根 87% → `3012ms` **53 根 210/210 = 100%**。滑行段不受影响（起点仍 -210px、到位 446ms）。

> ⭐ 探针也踩了一次：条的 class 从 `rounded-[2px]` 改成 `rounded-full`，采样脚本的选择器没跟着改，测出来「波形永远不出现」。**差点当成代码 bug 去查**。改成按 DOM 结构（槽 → 容器 → 子元素）取，不再依赖 class 名。

### 02:08 波形放稀疏（commit `d17942c74`，并入 PR #699）

用户觉得上一版（2px 条 + 2px 间距 = 53 根）太密。改为 **2.5px 条 + 4px 间距 → 32 根**，铺满 204/210（97%）。根数照旧按槽宽算，不写死。

**⭐ 连带项：采样间隔要跟着条数走**。条少了，50ms 会让一行 1.6s 就填满，滚动感一闪而过。改 70ms → 32 根约 2.2s，与之前节奏相当。**「条宽/间距」「根数」「采样间隔」是一组联动参数，改一个必须复算另外两个**，否则视觉节奏就散了。

### 02:15 波形参数三连调（`d17942c74` / `b1cc980f8` / `d3c6ce327`，均并入 PR #699）

用户对波形连提三次，逐步收敛：

1. **放稀疏**（`d17942c74`）：2px 条 + 2px 间距 = 53 根太密 → 2.5px + 4px = 32 根
2. **条宽加粗**（`b1cc980f8`）：2.5px → 4px，根数随之 32 → 26
3. **无声处成圆点**（`d3c6ce327`）：最小高度从写死 5px 改为 **`BAR_MIN = BAR_W`**，配全圆角，level=0 时正好是 4×4 的正圆

**⭐ 「条宽/间距」「根数」「采样间隔」是一组联动参数**，每次只改其一都要复算另外两个：根数由槽宽自动算（不用手动改），但采样间隔必须跟着调，否则铺满一行的时长会漂（50→70→85ms，始终维持约 2.2s）。这条已写进 `docs/chat-voice-input.md`，免得下次改条宽时又忘。

**⭐ 最小高度直接等于条宽**，比写个魔法数字 5 更能表达意图——「无声就是个点」这个设计意图被编码进了常量关系，改条宽时圆点自动跟着变，不会退化成椭圆。

### 02:21 波形灵敏度抽成常量 + 噪声门限（commit `a57ed6351`，并入 PR #699）

用户问「对声音敏感度可以调吗」。能——就是 `useVoiceRecorder` 里 `Math.sqrt(rms) * 5` 的那个 **5**，写死在表达式里。抽成 `LEVEL_GAIN`，注释写清调大调小各是什么效果。

**⭐ 顺手补了 `NOISE_FLOOR`（RMS 0.015），因为上一条需求在真机上其实不成立**：「无声 = 圆点」只在 headless 的合成音频下看得出来，真机有环境底噪、RMS 永远不是 0，每格都会比圆点高一两像素。门限是让那个设计意图真正成立的前提。公式 `rms <= FLOOR ? 0 : min(1,(rms-FLOOR)*GAIN)` —— 门限之上的部分才参与增益，避免在门限附近突然跳一大截。

**验证**：fake 音频下条高分布 `[4,5,9,17]`，26 根里 22 根圆点、有声处 17px，门限没吃掉信号。

> ⭐ 教训：**在合成/理想输入下验过的视觉效果，不等于真实输入下成立**。fake 音频是干净的（静音就是绝对 0），真麦克风永远有底噪。这次是顺着「敏感度」这个问题才回头意识到上一条改动在真机上会失效。

### 02:37 语音输入加长按支路（commit `366b38737`，并入 PR #699）

**需求**：用户发来原型新版本（400 行，交互整个换了），要在现有基础上加长按录音——长按态下上滑锁定、左滑取消，拖到垃圾桶要有红色效果。

**⭐ 先分析再动手，发现我做的没白做**：新原型是「长按 + 滑动」与「轻点转免提」两条支路共存，而我已实现的那套 = 免提支路。所以是**补**长按支路，不是重写。

**实现**：按住 220ms（或位移 >10px）进长按态 → 浮出锁与提示条；松手时手指在哪决定结果（垃圾桶=取消 / 锁=转免提 / 其他=发送）。长按态隐藏发送按钮（松手即发，按钮多余且手指按着点不到）。`pointercancel` 走取消。

**⭐ 两处必须偏离原型，都是「固定画板 vs 真实运行时」的差异**
1. **指针事件挂 `window`，不能用 `setPointerCapture`** —— 原型的 `.talk` 只是 `display:none`、元素还在 DOM 里所以捕获有效；我们这边**录音一开始 pill 就被录音条换掉、从 DOM 消失**，捕获随之失效，后续 move/up 全收不到。
2. **锁的纵向位置现测** —— 原型是 774px 固定画板里的绝对像素（`bottom:150px`）。真机输入条跟着键盘上抬，写死必飘。**这正是之前被删掉的 `CancelTarget` 里 `TARGET_GAP` 注释踩过的同一个坑**——同一个坑在这个项目里踩第二次了。

**验证**：CDP 真实指针事件跑四条支路，全部通过（含 transform 数值断言：锁 `matrix(0.12,0,0,0.12,0,54)`、垃圾桶 `scale(1.18)` + 红）。三态截图已发用户。

### 02:53 锁停在条上方 100px + 跟手（commit `1965b74e3`，并入 PR #699）

**需求**：锁的悬浮球不要贴着输入条，默认在上方 100px，手超过 100px 后球跟着手走。

**做法**：`LOCK_REST_ABOVE = 100`；`lockY = min(停放位, 手指y)`。**取 min 而不是直接跟手**——直接跟手的话，手指刚过 100px 阈值时球会「往下跳」去迎合手指（因为按下点在条内部，过阈值时手指仍低于停放位）。取 min 让球在手指够到之前岿然不动，够到之后无缝被拎走，没有跳变。

**⭐ 顺带修了自己刚引入的遮挡**：提示条原本钉在锁的**停放位上方**。锁被拎起来后只会往上走 → 必然压在提示条上。**是看截图才发现的**，几何数据全对但视觉是错的。改钉到录音条正上方（停放位与条之间的空档），两者永不相撞。

**实测**（barTop=729）：停放锁心 629（正好 100px）；上滑 40/90px 锁不动；130px 起锁心与手指 y 完全一致（621/551/451）；提示条全程 703 不飞；横向右移 70px 锁心 x 170→240。

> ⭐ 教训：**数值断言全绿不等于视觉正确**。这次锁的坐标、阈值、跟手全部符合预期，但两个元素重叠了——重叠不在任何一条断言的覆盖范围里。凡是新增浮层元素，必须看一眼截图。

### 03:10 强化拖入垃圾桶与锁定态反馈（commit `45363fc6e`，并入 PR #699）

用户一次提五项：垃圾桶变红后图标变大左旋、红底探出蓝条但不多、波形与计时向左收回（划出再回来）、锁定与进桶都要震动、锁定态球转红放大。全部实现并逐项实测。

**⭐ 踩到 CSS 优先级坑**：第一版把「入场淡入」和「收回淡出」写在同一层 —— `animation-fill-mode: both` 的**填充值优先级高于内联样式**，`opacity` 被入场动画的终值 `1` 永久盖住，波形只平移、不淡出。拆成两层（外层管入场、内层管收回）才对。

> ⭐ **这个 bug 是 `getComputedStyle` 探针抓出来的**：写的是 `0`、算出来是 `1`。截图上只表现为「淡出得不明显」，很容易看漏。**断言要读计算值，不要读自己写进去的值** —— 后者只能证明代码跑到了，证明不了它生效。

另一条设计判断：**进入判定区就震动**（不只在松手时），因为手指正压着按钮、视觉反馈多半被自己挡住，触觉才是可靠通道。vibrate 序列实测 `[12,10,10]`（开始 + 进桶 + 锁定）。

### 03:17 锁跟手改为横向 1:1、纵向 1/3（commit `b205273da`，并入 PR #699）

**需求**：拖动时横向速度与手位移一致，纵向为手位移的 1/3。

`lockY = 停放位 + min(0, 手指y − 按下y) × 1/3`。**纵向要拖慢是有原因的**：锁定判定行程 100px，而锁离起点也正好 100px —— 1:1 的话手指还没滑到阈值，锁早被顶出屏幕了。横向没这个约束，跟满才跟手。`min(0, …)` 保证往下拖不会把锁压回录音条里。

**实测**：纵向六个取样点（手 30/60/100/150/210/300 → 锁 10/20/33/50/70/100）逐项等于手位移/3；横向四个点锁 x 与手 x 完全一致；下拖 80px 锁停在停放位。

> 这条改动替换了上一版「手指够到锁才 1:1 拎着走」的 min 逻辑 —— 比例跟手更可控，也顺带解决了「锁被顶出屏幕」这个 1:1 必然会撞上的问题。

### 03:54 修多指误发 + 切后台取消录音（commit `17bea3426`，并入 PR #699）

用户报两个问题，都是真的：

1. **⚠️ 第二根手指会误发第一根手指的录音** —— 手势监听挂在 `window` 上却**没按 `pointerId` 过滤**，任何一根手指的 `pointerup` 都会走 `onUp` → `finish(true)`。按下时记住 id，move/up/cancel 只认这一根；已有手指在按时忽略第二根按下。
2. **切到后台要取消录音** —— `visibilitychange` → hidden 时丢弃。后台麦克风被系统挂起，继续录只会得到静音或半截音频；界面又看不见，「还在录」是隐蔽状态。丢弃而非发送，与 `pointercancel` 同一条原则。同时清手势状态（切后台后那根手指的 pointerup 多半永远不会来）。

**⭐ 测试脚本自己先错了一版**：CDP `Input.dispatchTouchEvent` 的 `touchEnd` 里 `touchPoints` 是**被抬起的点**，不是剩余的点。我按「剩余」传，实际抬起的是第一根手指，于是看到一次「发送」，**差点当成修复失败去改代码**。

> ⭐⭐ 救回来的是**事件轨迹**：打了 `pointerdown#2 → pointerdown#3 → pointerup#2`，一眼看出抬起的是 #2（第一根）而不是 #3。**只看结果（录音条没了）分不清「误发」和「正确发送」，必须看事件序列**。排查手势类问题，先把事件流打出来再下结论。
