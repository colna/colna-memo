### 追加 — 「松手还在录制」根因:锁的范围包住了网络上传(commit 39f6732dd)

用户反馈「有时候松手还在录制」。三种可能:`pointerup` 没送到 / `stop()` 不 resolve / **`finish()` 被丢弃**。是第三种。

`useLockFn` 的语义是**锁住期间的调用静默 `return`**,而 `finish` 的锁一直握到 `await sendVoice()` 结束 —— `voice.onSend` 是真上传(`onSendAudio` → File → TIM → COS),慢网几秒。

```
录第一条 → 松手 → finish 拿锁 → stop() → setRecording(false) → await sendVoice()  ← 锁没放
                                       ↓ 上传还在飞
再按住录第二条(startRecording 检查的是 recording/starting,都 false → 正常开录)
松手 → finish() → lockRef 仍为 true → return   ← 这一下被吞了
```

于是 `stop()` 没调、`recording` 没清:药丸停在录音态、麦克风常开、计时继续。之后再按也被 `if (recording) return` 挡掉,**只能切文字模式(卸载组件)才恢复**。「有时候」= 网快时上传几百毫秒撞不上,连发两条语音必现。

**判据**:第二次松手时控制台不打 `ChatVoiceRecorder finish`。

**修法**:锁只该罩住 `stop()`,不该罩住网络。
- `finish` 从 `useLockFn` 换成显式 `finishingRef`,只在 `await stop()` 期间置位(`try/finally`)
- `sendVoice` 移到锁外,`void` 掉不 await(它自己 try/catch,不会 reject)
- 手势 handler 不能读 `recording` **state** 判活 —— `pointerup` 比 React commit 快。新增 `recordingRef` + `setRecordingNow()` 同步双写,`finish`/`handlePointerMove` 一律读 ref

**代价**:两条语音可能并发上传、顺序不保证。但锁本来也只是「顺带」串行化,不是设计意图;真要保序得单开发送队列。

**验证**:写 Node 状态机仿真跑三个场景(正常 / 授权中松手 / 上传未完成就录第二条):

| 场景 | 旧 | 新 |
|---|---|---|
| 正常录发 | 正常,发 1 | 正常,发 1 |
| 授权中松手 | 正常,发 1 | 正常,发 1 |
| **上传未完成就录第二条** | **★卡住**,`finish DROPPED`,只发 1 | 正常,发 2 |

### 关键教训

- **`useLockFn` 是「防连点」,不是「临界区」**。它包住的整个 async body 期间,所有调用都被**静默丢弃**(不是排队)。一旦 body 里含网络请求,任何依赖「这次调用一定会执行」的**状态机终态**都会漏。凡是「按下-松开」这类必须成对的手势,终态转换绝不能放在会吞调用的锁里。
- 同源风险:`ChatInputBar.handleSend`(文字)也是 `useLockFn` 包着 `await text.onSend`。文字是点击式、没有「必须成对」的终态,所以只是发送期间点不动,不会卡死。**但这个模式在手势场景下就是 bug**。
- **读代码定不了性的东西就仿真**。本机无浏览器,把两版状态机搬进 Node、用 `setTimeout` 造 grant/stop/upload 时序,20 行就把「第二次 finish 被丢弃」跑了出来。比盯着代码猜快得多。

### 追加 — 弹窗不自动消失(commit 21269e1c7)

**根因:effect 依赖了每次渲染都换引用的回调,而父组件每秒重渲染。**

```tsx
// Chat/index.tsx:490 —— 内联箭头,每次渲染新引用
onCloseReward={() => { setRewardPopup({open:false,cents:0}); ... }}

// RewardPopup.tsx —— 依赖它
useEffect(() => { ...setTimeout(onClose, 2000) }, [open, onClose]);
```

`useTaskCountdown` 每 1000ms tick → `setReplyWindow` → **Chat 每秒重渲染** → `onClose` 新引用 →
effect 重挂 → `clearTimeout` 两个计时器再从零计时。**1.6s 淡出和 2.0s 关闭永远到不了。**

> 那个每秒渲染是我自己在 PR #565 里把 `replyWindow` 提到 Chat 上造成的。

**修法**:`onCloseRef` 存回调,`useEffect(..., [open])`。

**为什么以前没暴露**:旧弹窗依赖同样是错的,但走 `ModalContainer`,有遮罩可以点掉。
我按原型改成 `pointer-events:none` 后,计时器成了唯一出路 → bug 从「计时不准」升级成「永远关不掉」。

**验证**:Node 仿真 effect 重挂语义,父组件每 1s 触发一次:

| | 3s 后淡出 | 3s 后关闭 | effect 重挂次数 |
|---|---|---|---|
| 旧 `deps=[open, onClose]` | ✗ | ✗ | 3 |
| 新 `deps=[open]` + ref | ✓ | ✓ | 1 |

### 关键教训

- **`useEffect` 里带计时器 + deps 含回调 = 定时炸弹**。只要父组件周期性重渲染(倒计时、轮询、ws 推送),
  计时器就被无限重置,**且不报错、不告警**。
  → **回调进 ref,deps 只留真正的「开关」state。**
- **「移除逃生出口」会把潜伏 bug 变成致命 bug**。原来有遮罩可点,依赖写错也只是「关得早/晚」;
  改成 `pointer-events:none` 之后,同一个错误直接锁死 UI。**删兜底交互前,先确认主路径是对的。**
- **组件内部要能扛住调用方传内联函数**。不能假设 caller 会 `useCallback`;把回调存 ref 是组件自己的责任。
