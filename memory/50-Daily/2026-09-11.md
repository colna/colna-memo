| 文件 | 改动 |
|---|---|

| `web/components/aigc/create-workspace.tsx` | `RefImages` 加 `inline` 分路：内联走 `inlineRef()`（>2MB 先 canvas 缩到长边 2048 再 JPEG/PNG 重编码）不传 OSS；加 window 级 `paste` 监听收剪贴板图片 |
| `worker/src/generation.ts` | 出图成功后 `dropInlineRefs()` 把 params 里的 `data:` 参考图抹掉，只留 `refImageCount` |
| `web/lib/generation-view.ts` | 参考图张数优先读 `refImageCount`，兜底 `images.length` |
| `web/app/api/generations/route.ts` | 重新生成时若 `refImageCount > images.length` → 400「参考图未留存」 |
| `api-clients/src/drivers/golden.test.ts` | 补多图 `image[]` + 超 4 张拦截两条用例 |

**关键判断**

- **`inline` 必须做成 per-driver 开关，不能全局改**。视频 driver（kling / seedance / novita）是把 `input.images` 原样塞进 JSON body 交供应方按 URL 回拉，喂 data URI 直接炸。只有 gpt-image 走 `/images/edits` multipart 才吃得下 base64。
- **base64 必须用完即清**。`create/page.tsx` 和 `requirements/[id]/page.tsx` 的列表查询在服务端 `select` 了完整 `params`（一次 50 条），若每条压着 2MB base64，SSR 直接被拖垮。张数移到 `refImageCount` 才能保住列表上「参考图 ×N / 图生图」的标注。
- **清了就不能原样重发**，否则「重新生成」会静默退化成文生图 —— 所以在 API 层挡掉并提示重新选图。失败记录不清，留着重试。
- 粘贴用 window 级监听而不是放置区 `onPaste`：div 不可聚焦收不到事件；只处理 `clipboardData.files` 里的图片，粘贴纯文本不带 files，不会误伤提示词输入框。

## 工作日志 — 15:2x · 仓鼠卡改成正方形（`f4711397`）

上一版只是把横卡放大，用户反馈「还是没展示全仓鼠」。

**量了素材才找到根因**：用 ffmpeg 把 `play-phone.mp4` 按 4fps 抽成 216² 的 raw，逐帧和背景色（#FEFEFE）比对，取所有帧的并集包围盒 —— 仓鼠纵向占 **9%–98%**、横向占 **4%–94%**，几乎顶满 1080 见方的画面。也就是说卡只要不是正方形，`contentFit="cover"` 就一定从头顶或脚底切进仓鼠身上，**放大多少都没用**。原来注释里写的「裁掉的是空白桌面」是错的。

**改法**：边长由页头高度反推（`ACTION_CARD_HEIGHT * 2 + HEADER_GAP` = 134），删掉 `PET_WIDTH_RATIO`；窄屏上 `PET_MAX_SHARE = 0.44` 先夹住边长，再反过来压低入口卡高度，保证永远是方的。`PeoplePetCard` 的 `width` / `height` 收成一个 `size`，把「必须是方的」变成签名上的约束而不是注释里的约定。

**沉淀**：`contentFit="cover"` 出现裁切问题时，先量**素材里主体占画面的比例**，再决定是调容器尺寸还是调容器**比例**。主体顶满画面时，只有让容器比例等于素材比例才不裁；单纯放大容器是无效操作。

## 工作日志 — 19:00 查清 `sitin-rn/.fastembed_cache` 是什么（诊断，未删）

用户问「fastembed_cache 是干什么的」，顺带把它为什么长在 RN 仓根查清了。

- **它是什么**：`fastembed`（Rust crate）的模型缓存，里面只有一个
  `models--intfloat--multilingual-e5-base`（1.0 GB 权重 + 17 MB tokenizer）。colna 的语义检索靠它 ——
  `colna-memo/src/embedder.rs` 用 `EmbeddingModel::MultilingualE5Base`（768 维、中英多语言）。
- **为什么在 sitin-rn**：fastembed 4.9.1 `src/common.rs` 里 `DEFAULT_CACHE_DIR = ".fastembed_cache"`
  是**相对路径、按进程 cwd 解析**，且 `FASTEMBED_CACHE_DIR` 没设（colna 源码里 `grep FASTEMBED` 无命中）
  → **在哪个目录调 colna，模型就下到哪个目录**。用绝对路径调也一样：绝对路径只决定跑哪个二进制。
  仓根那份的时间戳 18:19–18:22 就是一次 cwd = sitin-rn 的 colna 调用留下的，1.1 GB 网络重下。
- **KB 根那份才是正主**（1.5 GB，含 e5-base 与 7/31 的 e5-small）；sitin-rn 这份是可再生的副本，
  删了不丢数据（下次在 sitin-rn 里跑又会重下）。
- **现状**：**没删**（等用户点头）；要不要给 sitin-rn 的 `.gitignore` 加一条也待定 —— 倾向不加：
  它再冒出来就说明又在错的目录跑了 colna。
- **沉淀**：[colna 的模型缓存会落在「当前目录」](../30-Resources/troubleshooting/colna-fastembed-cache.md)
  （源码两行 + 处置三条：删杂散副本、`FASTEMBED_CACHE_DIR`、别指望绝对路径）。
