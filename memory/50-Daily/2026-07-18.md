### P1-1（我 refactor 引入的回归）：编排挂错层

- **根因**：`useVideoTipsCall` 原挂在 chat 页（`ActiveChat` 内）。接通后 `useWebCall` 会 `navigate("/video-call")`，而 `/video-call` 是 `/chat` 的**对等 Route，会卸载整个 `/chat` 子树** → hook 随之卸载：60s 限时 timer 在接通瞬间被 effect cleanup 清、结束时 onEnd 已不在 → **web 仍不在 1min 自动挂、奖励也丢**。
- **修法**：hook 改成**自包含、无 chat 依赖、无参数**，随 `CallControllers` 常驻挂在 App 根（新增 `VideoTipsCallController`，和 `MockCallController` 同级——平台无关、通话中不卸载）。自订阅全部通话事件；接通记 `beginTime` + arm 60s timer→`WebCallManager.hangup()`；结束按自记时长 `≥ LIMITED_CALL_MIN_PAID_DURATION_S`(30s) 判发奖，金额取发起时 `centsPerMinute`（`/100` 转美元传 startCall），金币动画走全局 `modalStore`（不经 chat 的 mountedRef gate）；接通前失败（拒接/取消/未接）走 `onAbort` 只复位不发奖，防 activeRef 泄漏误判下一通。

### P1-2（既有严重 bug）：native 主叫漏复位 isEnded

- **根因**：native `isEnded` ref 只在**被叫入口**（`handleNativeCallInvited`）复位，**主叫入口**（`handleOutgoingStart`）漏了 → 第 2 通及以后主叫，上一通结束置的 `isEnded=true` 残留，`handleNativeCallEnd` 被 `if(isEnded.current) return` 直接吞 → 订单结钱了但结算/发奖/导航回退全丢。web 的 `beginCallLifecycle` 两个入口都复位、native 只做了一半。
- **修法**：`handleOutgoingStart` 拿到 targetUserId 后补 `isEnded.current = false`。

### 值得记的判断

- **⭐ 挂载层决定生命周期**：`CallControllers.tsx:40` 二选一挂 web/native controller，**挂在这里的 hook 通话全程不卸载**（它是 `<AppRouter/>` 的 sibling，不随路由变）；挂在 `/chat` 里的 hook 一旦 `navigate("/video-call")` 就连同 timer/监听一起没。**凡「跨接通、跨导航要活着」的编排，必须挂常驻层，不能挂随路由卸载的页面。** 这正是我 refactor 时踩的坑——把限时从常驻的 useWebCall 挪进了会卸载的 chat 页。
- **native 无 hangup**：到点 `WebCallManager.hangup()` 在 native 是 no-op（挂断归 APK）。native 的限时挂断本 hook 不负责，是独立缺口（已在昨日 #646 body 记为 follow-up）。
- **web/native 两个入口的对称复位**：web `beginCallLifecycle` 抽成一处两入口都调、不易漏；native 是两处手写 `isEnded=false`，天然容易只改一处——这次补的就是漏的那处。

## 工作日志 — 消息刷新后缺一段：真因 DataCloneError（IndexedDB 整批事务失败）

- **现象**：进会话后写缓存 45 条，刷新回来 L2 只读到 37，缺的一段要等 revalidate 从服务端重拉；**每次刷新都稳定 37**。
- **真因**（实测日志坐实）：`L2 落盘失败 { name: "DataCloneError", message: "Failed to execute 'put': function(e2){ this.instanceID=..., this.sizeType=.., this.type=0, this.size=.. } could not be cloned" }`。
  - IndexedDB 走**结构化克隆、不接受函数**，而 TIM **图片/文件类消息**的 `payload` 上挂着 SDK 的类/方法。
  - 致命点：`put` 失败会让**整个事务**失败 —— 会话里只要有一条这种消息，整批 45 条就永远写不进去；盘上卡死在最后一次成功的 37 条，之后所有新消息刷新即丢。
  - 而 `flush()` 的 catch **完全静默**且自动回滚重试 → 永远失败、永远无声，外部完全无感。
- **修法**（commit `8a4fe3e24`，实测通过）：`queueL2` 存盘前对每条 `raw` 做 JSON 往返只留可序列化数据（`formatMessage` 读的都是纯字段，不依赖原型/方法）；**个别消息序列化失败就跳过它，不连累整批**。日志加 `droppedUnserializable`。
- **保留的独立修复**：`writeBatch` 补 `tx.onabort`（配额超限走 abort 不走 error，漏了会让 Promise 永远悬着）+ 写盘成功/失败日志。
- **撤掉的错误改动**（commit `29f23a9ea`）：`pagehide`/`visibilitychange` 兜底 flush、防抖改节流 —— 基于「防抖没落盘」的错误诊断，不是本 bug 的解。

### 值得记的判断

- **⭐⭐ 我连错两版方向，根源是「没让失败说话」**：前两版（加卸载兜底 flush、防抖改节流）改的都是「**什么时候写**」，而真相是「**根本写不进去**」。转折点是给静默的 `catch` 加上日志 —— **一个吞掉异常的 catch，能让人朝错误方向修无数遍**。排查时优先把「静默失败」暴露出来，再谈修法。
- **⭐ IndexedDB 存 SDK 对象前必须净化**：结构化克隆不接受函数。TIM 的 `Message.payload` 在图片/文件类消息上挂着类实例/方法，直接存必炸。而且 `os.put` 对不可克隆值是**同步抛错**、不走 `tx.onerror`。
- **⭐ 批量写要有「单条坏数据不拖垮整批」的隔离**：本 bug 的破坏力全来自「一条不可克隆 → 整个事务失败 → 整个会话缓存永久写不进」。批处理里凡是单元素可能失败的，都要么先净化、要么逐条降级。
- **`tx.onabort` 不能漏**：配额超限等情况事务是 abort 而非 error，只听 `onerror` 会让 Promise 永远悬着（既不 resolve 也不 reject）。
- **诊断链条本身值得复盘**：稳定复现（每次都 37）→ 排除随机丢失；`afterTtl==onDisk` → 排除 TTL；`queued(45) != onDisk(37)` → 锁定「写不进」而非「读丢失」；最后靠 catch 日志拿到 error.name 定案。**每一步都是先用日志把一类可能排除掉，而不是猜。**

### 口径确认（产品）

**「只要真的拨出去了就算任务完成」** —— 对方接没接都不影响：接通挂断/拒接/忙线/未接/取消一律发记录带 taskId 并删卡。唯一例外 `aborted`（权限拒/建单失败）压根没拨出去，不发记录不删卡、卡留着可重来。**界线是「有没有真的发起呼叫」，不是「对方接没接」。** 原注释写反了（写的是「点了没打成就别删卡」），4 处统一改正。

### ⭐⭐ 值得记的教训

- **⭐ 我又误判了一次，而且是同一个毛病**：用户问 `centsPerMinute: 0` 时我说「更可能是**数据侧**问题而非取值路径错」，CR 一查是**取值路径 bug**（少个 `|| 兜底`）。加上之前「切不动会话」误回滚无辜改动，**两次都是没查到底就下结论**。凡涉及钱和资损，"看起来像数据问题"这种判断必须落到代码上验证再说。
- **⭐ 双人 CR 捞出了我自己看不见的两类东西**：① 资损 P1（我改了那么多遍都没注意发卡处缺兜底）② **我自己新改动引入的风险**（卡不当场删 → 重复点击窗口）。自审最容易漏的就是「我这次改动的副作用」。
- **⭐「给无归属的全局标记加归属 + 时效」这招第二次用了**：先是 `limited` 漂移（加对端 id + TTL），这次是 `pendingVideoTipsTaskId` 泄漏（同样加对端 id + TTL）。**模块级单槽 + 存在静默返回路径 = 必然泄漏**，这是个会反复出现的模式，见到就该警觉。
- **`0` 不是 nullish**：`??` 和 `||` 在「0 是合法值还是该兜底」上语义相反。金额这类字段用 `??` 容易把 0 当有效值传下去，而 0 恰恰是最该兜底的。
