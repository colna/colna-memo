### P1-1（我 refactor 引入的回归）：编排挂错层

- **根因**：`useVideoTipsCall` 原挂在 chat 页（`ActiveChat` 内）。接通后 `useWebCall` 会 `navigate("/video-call")`，而 `/video-call` 是 `/chat` 的**对等 Route，会卸载整个 `/chat` 子树** → hook 随之卸载：60s 限时 timer 在接通瞬间被 effect cleanup 清、结束时 onEnd 已不在 → **web 仍不在 1min 自动挂、奖励也丢**。
- **修法**：hook 改成**自包含、无 chat 依赖、无参数**，随 `CallControllers` 常驻挂在 App 根（新增 `VideoTipsCallController`，和 `MockCallController` 同级——平台无关、通话中不卸载）。自订阅全部通话事件；接通记 `beginTime` + arm 60s timer→`WebCallManager.hangup()`；结束按自记时长 `≥ LIMITED_CALL_MIN_PAID_DURATION_S`(30s) 判发奖，金额取发起时 `centsPerMinute`（`/100` 转美元传 startCall），金币动画走全局 `modalStore`（不经 chat 的 mountedRef gate）；接通前失败（拒接/取消/未接）走 `onAbort` 只复位不发奖，防 activeRef 泄漏误判下一通。

### P1-2（既有严重 bug）：native 主叫漏复位 isEnded

- **根因**：native `isEnded` ref 只在**被叫入口**（`handleNativeCallInvited`）复位，**主叫入口**（`handleOutgoingStart`）漏了 → 第 2 通及以后主叫，上一通结束置的 `isEnded=true` 残留，`handleNativeCallEnd` 被 `if(isEnded.current) return` 直接吞 → 订单结钱了但结算/发奖/导航回退全丢。web 的 `beginCallLifecycle` 两个入口都复位、native 只做了一半。
- **修法**：`handleOutgoingStart` 拿到 targetUserId 后补 `isEnded.current = false`。

### 值得记的判断

- **⭐ 挂载层决定生命周期**：`CallControllers.tsx:40` 二选一挂 web/native controller，**挂在这里的 hook 通话全程不卸载**（它是 `<AppRouter/>` 的 sibling，不随路由变）；挂在 `/chat` 里的 hook 一旦 `navigate("/video-call")` 就连同 timer/监听一起没。**凡「跨接通、跨导航要活着」的编排，必须挂常驻层，不能挂随路由卸载的页面。** 这正是我 refactor 时踩的坑——把限时从常驻的 useWebCall 挪进了会卸载的 chat 页。
- **native 无 hangup**：到点 `WebCallManager.hangup()` 在 native 是 no-op（挂断归 APK）。native 的限时挂断本 hook 不负责，是独立缺口（已在昨日 #646 body 记为 follow-up）。
- **web/native 两个入口的对称复位**：web `beginCallLifecycle` 抽成一处两入口都调、不易漏；native 是两处手写 `isEnded=false`，天然容易只改一处——这次补的就是漏的那处。
- 沉淀补进 [[../30-Resources/troubleshooting/pwa-call-order-lifecycle]]。

## 工作日志 — 通话架构 P2/P3 可前端安全落地部分（双击守卫 / activeRef 泄漏 / native 死 timer）

- **背景**：用户「都修了吧」。先按「先查再写」逐条对当前代码核对，发现 review 时列的 6 条 P2/P3 里，几条已被 #646/#647 缓解或是有意取舍，真正**能前端安全、正确、低资损修**的只有 3 条 → 修这 3 条，其余分类回报原因。commit `eb4a1d40a`（叠在 P1 `7afa232a2` 上），改 `useWebCall.tsx` / `useNativeCall.tsx` / `useVideoTipsCall.ts`。
- **改的 3 条**：
  1. **双击建单守卫**（web+native `handleOutgoingStart`）：权限检查+建单都是 await，两次快速点击会在第一次没建完单时重复建单（真金白银重复单）。加 `outgoingInFlightRef` 把整段串行化，进行中丢弃后到的，`finally` 复位。
  2. **videoTips activeRef 泄漏**：外呼在权限拒/建单失败时原本**静默 return，不发终止信号**，`useVideoTipsCall.activeRef` 残留 true → 把下一通无关通话误当 videoTips 处理（误挂断+误发奖）。web+native 失败路径改为 `emit CALL_OUTGOING_ENDED{reason:'aborted'}`，业务 hook `onAbort` 复位；`handleOutgoingEnded` 对 `aborted` 静默（不弹 toast，权限反馈由 `permissions.ts:134` 自行给）。native 环境 useWebCall 未挂载，该事件只被业务 hook 收到，无副作用。
  3. **native 死 timer**：`useVideoTipsCall` 在 native 上 arm 的 60s timer 到点调 `WebCallManager.hangup()` 是 no-op（native 挂断归 APK），只会误导 → 改为 `if (isApp()) return` 仅 web arm。
- **核对后判定「不改」的（附原因，非遗漏）**：
  - **native connectSession stale fields**：#646 的 `startCall` 已在建单时归零 `callBeginTime/callEndTime/endReason` 残留 → 当前不成立。
  - **P3 handleCallError closeConnect 缩窄订单悬空窗口**：#647 注释明确「悬空远好过错发钱」是**有意取舍**；缩窄需区分瞬时(5100 对方未推流/5000 视图未挂载，通话继续)vs 致命错误码，盲改会在通话中误清 session 或错发钱 → 需 SDK 错误码语义确认 + 测试环境验证，不宜盲改。
  - **native 无 handleCallError 对等回调**：GraceChat-Earn 无错误事件回传，PWA 加监听也无事件来 → 需 native 侧支持。
  - **reward.cents 量纲 / price 语义 / finishCallOrder 服务端幂等**：需后端确认口径，前端盲改直接资损。

### 值得记的判断

- **⭐「都修」不等于闷头改全部**：review 列的 finding 到动手时要**逐条对当前代码复核**——几条已被后续 PR（#646/#647）缓解、几条是**有意取舍**（#647 注释白纸黑字）、几条**盲改会资损或越权**（动钱口径/推翻既有决策）。专业做法是把「前端能安全正确修的」全落地，把「需后端/native 或有意取舍的」明确分类回报，而不是为了显得干活去改真金白银逻辑。
- **区分「静默 return」的代价**：外呼失败静默 return 看着无害，但上游有个按事件复位的状态机（videoTips activeRef）时，**没有终止信号 = 状态泄漏**。修 fire-and-forget 的 emit 架构，失败路径也要发信号。
- **平台无关 hook 里的平台差异**：`useVideoTipsCall` 是平台无关编排，但「能不能挂断」是平台能力差异（web 有 hangup / native 归 APK）→ 用 `isApp()` 在 hook 内分流，别 arm 到点 no-op 的死 timer。
