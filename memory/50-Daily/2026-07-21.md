### 11:xx InputBar 引导手势：文字态也要显示 → **PR #681**（`personal/zz/pwa-inputbar-hand-guide` → `feature/sitin4.0`，2 commits / 1 文件 +36 −8）

**需求**：现在只有 voice 按钮上有小手，文字输入 mode 下也要有 —— **要有都有，要没有都没有**。

**根因（渲染层，不是业务层）**：`ChatInputBar` 里 `railRef`（手势的测量锚点）**只挂在语音模式的容器上**；文字模式下 `railRef.current` 为 null，`useLayoutEffect` 里 `if (!el) return` 直接返回，`handAt` 永远是 null。

**业务条件本来就是统一的**：`ChatFooter` 传的 `handOnInput = !!pendingTask && (isRed || (isYellow && hasVoiceReward))` —— 只看会话状态，**与输入模式无关**。所以「要有都有」只需修渲染层，不用动业务判定。

**改了 4 处**（后两处是顺带查出的连带缺陷）
1. 文字态的 `<input>` 用回调 ref 同时挂 `textInputRef`（聚焦用）和 `railRef`（手势锚点）
2. `railRef` 类型 `HTMLDivElement` → `HTMLElement`（要兼容 div 和 input）
3. **`if (!el) return` 改为先 `setHandAt(null)`** —— 否则切换模式那一帧手势会停在上一个模式测出的坐标上
4. **effect 依赖加 `isVoice`** —— 切换模式换的是另一个锚点元素，而 **ref 的变化不触发重跑**，少了它同样会停在旧坐标

**⭐ 第二轮：我把「既有设计」当成了正确行为，判断错了。**

第一轮改完，用户实测反馈「文字态直接进入有手，但切换后手消失」。我当时在报告里写的是「手动点切换按钮会置 `hasInteracted`，手势本就该消失，那是既有设计」—— **这恰恰就是用户要消除的不一致**。

根因：`onPointerDownCapture` 在**捕获阶段**把「用户已开始使用」置位，而左侧的语音/键盘切换按钮**也在输入条内**，点它同样命中。修法：给切换按钮打 `data-mode-switch` 标记，捕获阶段 `closest("[data-mode-switch]")` 命中就豁免；其余点击（输入框/发送/相机/礼物/语音按压）行为不变。

**教训**：**用户说「要有都有」时，别急着把某个既有行为归为「设计如此」而排除在需求之外。** 我第一轮只修了「文字态没有锚点」，把「切换后消失」当成合理设计放过了，结果只解决了一半——用户的验证路径恰好走的是另一半。判断某行为是否属于需求范围时，应当以**用户描述的现象**为准，而不是以代码里的注释意图为准。

**⚠️ 视觉验证全程靠用户实测**：本机 dev server 起不来 —— 报 `_jsxDEV is not a function`（今天 pull 了 110 个 commit、lockfile 变了，而 `pnpm install` 被私有 registry 不可达阻塞；清 `.vite` 缓存重启无效）。

> ⭐ **靠一张截图定位问题的方法**：用户发来「没有手」的截图，URL 是 `?mode=voice` 却渲染成文字态、日志里有 `text.start` —— 两条合起来说明**发生过手动切换**（预览页没传 `disabled`，不会强制切态），而 `switchMode("text")` 里的 `focus()` 正好解释了 `text.start`。据此推断出「切换清掉了手势」，随后被用户实测证实。**截图里的 URL、日志条目、控件图标方向都是证据**，比追问用户操作步骤快。
>
> 另外给用户设计了**二分验证**：直接开 `?showHand=1`（文字态、什么都不点）—— 有手则证明第一轮改动生效、问题只在切换；没手则说明锚点改动根本没生效。一次操作就能把两种可能分开。

**Doc-first 检查**：`docs/dh-tutorial-chat-mode.md` 只列了 `ChatInputBar` 的 props 签名表，本次不改签名（`showHand?` 不变），无需更新文档。

### 01:xx browser-replay —— 从空仓库到可用（commit `b8ea740`）

**需求**：录制点击/输入/聚焦等事件 → 回放 → 导出 JSON 带 DOM 选择器，**禁止用 class 选择器**。

MV3 扩展，无构建、无 npm 运行时依赖。结构与架构决策见 [[../10-Projects/browser-replay]]。

**验证**：25 项断言全绿（选择器单测 9 + 端到端 16，后者用 CDP 发真实 isTrusted 事件录制再回放，断言表单数据完全一致）。

**四个坑**
1. **Chrome 150 禁用命令行 `--load-extension`**（flag 出现在 chrome://version 但扩展列表为空，无报错）。`--disable-features=…`、`--remote-debugging-pipe`、预置 developer_mode、headful 全试过无效。**用 3 行的最小 MV3 扩展做对照**才确认是浏览器限制而非自己 manifest 出错。
2. `npm i -D jsdom` 静默不装（反复 `up to date` 但 node_modules 不存在）→ 放弃，改 `chrome --dump-dom` 跑真 DOM 断言。
3. **点 checkbox 被误录成「输入 yes」** —— checkbox 也派发 `input`，`el.value` 是 value 属性不是用户输入。被「连续输入应合并成 2 步」这条**具体到值**的断言抓出来；而「录到了 click」这类过程断言全绿。
4. 点提交按钮同时录到 click + submit 两步，回放时第二步必失败 → `onSubmit` 里若上一步是 200ms 内的 click 就丢弃。

### 10:xx `PwaEarnDeduction` 主叫补传 price → **PR #678 已 merge**（2026-07-21 11:37 UTC，merge commit `097f365b`，并入 `feature/sitin4.0`）

> **遇到什么问题 → 怎么解决**
> - **怎么区分主被叫** → 不用新加标志，`ConnectSession.price` 天然就是（只在 `startOutgoingCall` 赋值，被叫路径不设），直接透传 `session?.price`。

> **残留**

> - [ ] 真机未验：主叫通话中触发 3 次违规 → 看扣减是否按 `price` 算

**需求**：pwa 端**主动发起**通话时调违规扣减接口要传 `price`，被动（被叫）不传。

**⭐ 前端不需要新加主叫标志** —— `ConnectSession.price` 天然就是这个语义：

| 路径 | `session.price` |
|---|---|
| 主叫 `startOutgoingCall` | `options?.price ?? OUTGOING_CALL_PRICE_PER_MIN`，**必有值**（`webCallManager:310` / `nativeCallManager:192`） |
| 被叫 | **不设**（`useWebCall:422` 那个 `price: releasePrice` 只传给接听弹窗展示，没写进 session） |

所以 `pwaEarnDeduction(orderId, session?.price)` 一行就区分了主被叫，判定逻辑一行不用加。

**为什么只有主叫要传**（`callerPayout.ts` 注释即证据）：被叫是通话中逐分钟入账、服务端握着单价；**主叫这一单的钱只在 `finishCallOrder` 一次性入账**，通话进行中服务端不知道单价，扣一分钟收益算不出金额。

**改动 3 处**
- `app-pwa/src/http/callApi.ts` — `pwaEarnDeduction(callOrderId, price?)`
- `app-pwa/src/hooks/useCallViolationDeduction.ts` — 传 `session?.price`
