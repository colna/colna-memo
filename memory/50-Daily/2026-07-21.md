### 07:xx Add 点击后验证 + 修 `buildError` 非法 selector（并入 PR #674，commit `db6e72517`）

**用户报告**：点 Add 有时不成功，页面弹 `Something went wrong.`（DOM：`<div class="tPHQ9 YvJ9J v0HEU"><svg/><span class="nonIntl">Something went wrong.</span></div>`）。要求点完后验证是否成功再返回结果。

**⭐ `span.nonIntl` 是关键线索**：nonIntl = Snapchat **不翻译**这段文案，所以 LABELS 里只放英文一条就够；真出现别的语言变体，反而说明选择器抓错了元素。

**改前的问题**：点完只 `log` 按钮状态，`result` 无条件返回 `added: true` —— **失败被记成成功**，behavior_log 不可信且不会重试。

**改法**：点击后轮询卡片直到落定
- 按钮变 Added/Pending → `added: true` + `buttonText`
- 出现失败 toast → `ADD_REJECTED`
- 6s 内两者都没有 → `ADD_UNCONFIRMED`（**故意报错**：上游可重试，而重试无害 —— 已加过的卡片会返回 ALREADY_ADDED；报成功反而把静默失败埋了）

三个细节：**点击前先记录已有 toast 并排除**（否则上一次失败残留的提示会让这次误判）；**每轮重新解析卡片**（点 Add 会重渲染该行，旧节点已 detach）；**先判失败再判成功**（toast 是确定信号，按钮没变只是尚未确定）。

**⭐⭐ 顺带查出我自己在 #671 里埋的 bug**：`utils.captureDomSnapshot` 里 `document.querySelector(selector)` **没有 try/catch**，而我在 clickMute 里传了 4 处 `"text:Message Notifications"` / `"text:Silent"` —— 这些**不是合法 CSS**，`querySelector` 抛 SyntaxError。因为它跑在 `buildError` 内部，**clickMute 的每一条失败路径都退化成了 `EXCEPTION`**，真实错误码和 DOM 快照全丢。

发现过程：我这次写 `selector: 'span:contains("Something went wrong.")'`，测试直接报 `code=EXCEPTION`。顺藤摸瓜才发现同类问题在已合并代码里有 4 处。**已用 Chrome 逐条验证**（`text:Silent` → SyntaxError，`span.nonIntl` → OK），不是推断。

修法：`captureDomSnapshot` 加 try/catch 并置 `selector_invalid` 标记（根本修复，防下一个人踩）+ 4 处改传 `"span"`（文案实际所在标签；"找的是哪句话"已在 message 里）。

**沉淀（⭐ 复用价值高）**

1. **`selector` 这类"给人看的定位描述"不能直接喂给 `querySelector`。** 想写 `text:xxx` / `:contains()` 这种伪语法时，要么放进 message，要么在消费端加 try/catch。**在错误处理路径里抛异常，代价是把真实错误换成一个假错误** —— 排查时看到的 `EXCEPTION` 与真实原因毫无关系。
2. **错误处理代码本身也要被测试覆盖。** 这 4 处非法 selector 只在失败路径上触发，正常流程永远碰不到，所以 #671 合并时没暴露。**只测 happy path 等于没测错误处理。**
3. **"点了" ≠ "成功了"。** 任何 UI 自动化在点击后都要有独立的成功判据（状态变化 / 失败提示），否则失败会被静默记成成功。这类 bug 在报表上完全看不出来，只有对账时才发现数量对不上。

**验证**：headless Chrome，13 项通过；唯一 FAIL 是既有 `utils.simulateClick` 双触发（已标注 pre-existing）。**这个双触发很可能就是 `Something went wrong.` 的成因之一** —— 请求在途时第二次激活到达，服务端拒绝正是典型表现。已写进 PR follow-up：修完它之后对比 `ADD_REJECTED` 发生率即可证实或排除。

**PR #674 现状**：4 commits / 5 files / +273 −177，标题 `exact-ID matching + post-click verification`，描述四节。

### 07:xx（续）双触发拿到生产实锤 → followUserById 改单次点击（commit `0a1c1830a`）

1. 代码级 —— `utils.simulateClick` 先 `dispatchEvent(click)` 又 `el.click()`
2. 浏览器级 —— fixture 里 handler 跑 2 次
3. **生产级 —— 用户日志里同一条查询出现 2 次**

**修法**：followUserById 内实现 `clickOnce()`（保留完整 pointer/mouse 序列，**只去掉 `el.click()`**）。保留序列是因为靠 pointerdown/mousedown 打开的菜单不响应孤立 click 事件；去掉 `el.click()` 安全，因为它只是再 dispatch 一个 click，而 activation behavior 已经由前一个 dispatch 触发了。

### 02:xx browser-replay 修「无标识元素导致回放中断」（commit `8971db5`）

**现象**（用户实测）：回放停在第 2 步，`等待超时（10000ms）：focus #root > div:nth-of-type(1) > div:nth-of-type(2) > nav > … > div`。

**根因是三个缺陷叠加，不是一个 bug**：

1. **录了无意义的聚焦** —— SPA 常给布局容器挂 `tabindex`，点击时它真的拿到焦点，于是每次点击都多出一个 focus 步骤。而这类元素没有任何稳定标识，只能退到 8 层结构路径，**是整条脚本里最先失效的部分**。修法：只录输入类元素（input / textarea / select / contenteditable）的聚焦 —— 按钮的焦点由 click 自带，布局容器的焦点不影响任何状态。
2. **失败即停** —— 一个可有可无的 focus 挂掉，后面几十步真正有用的操作全被拦下。修法：focus / blur / scroll 失败跳过继续（等待上限 10s → 2s），关键步骤失败才中断。另外这三类步骤**不再要求元素「可交互」**：布局容器塌陷成 0 尺寸很常见，但 `el.focus()` 照样有效，硬套可交互判定只会让它们永远等不到。
3. **报错说不清原因** —— 「等待超时」分不清是「页面上没这个元素」还是「找到了但不可交互」。修法：区分两者，并列出尝试过的每个选择器**各匹配到几个元素**。

**顺带修掉同源的第四个问题**：结构路径从 `html > body` 一路铺下来。改为从最近的锚点或 `nav` / `main` / `form` 等**地标标签**起算，并把**文本线索提到结构路径之前**尝试（6 层路径插进一个包装层就全废，按钮上的文字改版后通常还在）。

**沉淀（⭐ 复用价值高）**

1. **「顺带发生的事件」不等于「用户的动作」。** focus 是点击的副产物，录进脚本就成了一个必须成功、却最容易失败的步骤。录制类工具要先分清「用户意图」和「浏览器的连带反应」，后者只在它本身改变状态时才值得记。
2. **失败处理要按「这步失败会不会让后面变得没意义」分级**，而不是一刀切。focus 失败后面照跑不误，click 失败后面全是噪声 —— 同一个 `if (!ok) return` 对两者都不对。
3. **超时报错必须带上「我试了什么、各匹配到几个」**。「等待超时」这四个字让用户完全无从下手；「`#x` → 0 个匹配」直接就能判断是页面改版还是选择器错了。
4. **兜底顺序要按可靠性排，不能按生成顺序排。** 原来 resolve 是「先试完所有 CSS 候选、再用文本兜底」，等于让最脆的 6 层结构路径优先于最稳的文本。改成按 score 分段：语义候选 → 文本 → 结构路径。

**测试**：选择器单测 9 → 11 项，端到端 16 → 24 项，新增「布局容器的聚焦未被录制」「失效的聚焦跳过而关键步骤中断」「结构路径失效后靠文本兜底」「结构路径从地标起算」。全绿。

### 02:xx（续）点击上溯到可交互祖先（commit `e910997`）

**用户追问**：`nav > div:nth-of-type(2) > … > span:nth-of-type(1) > span > span`（11 层）这种查找方式精准吗？

**回答要分两层**：录制那一刻它精准（生成时验证过唯一命中），但**下次几乎必然失效**（任何一层多个包装 div 就全废）。用户真正该关心的是后者。

**但根本问题是这条路径不该长成这样**：`span > span > span` 说明录制器记的是**事件的 `target`** —— 点一个按钮时 target 往往是按钮里的 `<span><span>文字</span></span>`，这些包裹层没有任何标识；而外面那个按钮多半带着 `aria-label` 或 `data-testid`。

**修法**：目标自身只能退到结构路径时（score < 60），向上找最近的**可交互元素**（button / a[href] / [role=button] / 表单元素），且**必须确实更好认才换** —— 择优不是无脑上溯。只上溯到可交互元素而不是布局容器：回放点击取元素中心点，容器太大时中心可能落在别的子元素上。

实测由 `span > span > span` 变成 `button[aria-label="收藏此项"]`。

**顺带**：步骤页对 score < 60 的步骤标「⚠ 易失效」，让用户自己能看出哪几步是靠结构路径吊着的。

**沉淀（⭐）**

1. **事件的 `target` ≠ 用户的意图对象。** 用户点的是"按钮"，DOM 给你的是按钮里最深的那个文字节点。任何基于 DOM 事件做录制/埋点/热图的工具都要处理这层落差，否则记下来的全是无标识的包裹层。
2. **"精准"和"稳定"是两个问题，别混答。** 一个 11 层路径可以做到 100% 唯一命中（精准），同时 100% 活不过下次改版（不稳定）。用户问"精准吗"时，通常真正想知道的是后者。
3. **择优上溯 > 无脑上溯。** 只在自身不好认时才向上找，且新目标必须评分更高。一刀切上溯会把"点列表第 3 项"变成"点整个列表"。
4. **脆弱性要在 UI 上可见。** 分值藏在 JSON 里等于没有；标在步骤页上，用户才知道该给哪几个元素加 `data-testid`——那才是治本的动作。

**残留**
- [ ] `background.js` 的存储与跨页面调度**未被自动化覆盖**（Chrome 禁用 `--load-extension` 所致），需手动装载扩展验一次：录一段带页面跳转的流程 → 回放看游标能否续跑
