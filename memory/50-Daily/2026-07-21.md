### 01:xx browser-replay —— 从空仓库到可用（commit `b8ea740`）

**需求**：录制点击/输入/聚焦等事件 → 回放 → 导出 JSON 带 DOM 选择器，**禁止用 class 选择器**。

MV3 扩展，无构建、无 npm 运行时依赖。结构与架构决策见 [[../10-Projects/browser-replay]]。

**验证**：25 项断言全绿（选择器单测 9 + 端到端 16，后者用 CDP 发真实 isTrusted 事件录制再回放，断言表单数据完全一致）。

**四个坑**
1. **Chrome 150 禁用命令行 `--load-extension`**（flag 出现在 chrome://version 但扩展列表为空，无报错）。`--disable-features=…`、`--remote-debugging-pipe`、预置 developer_mode、headful 全试过无效。**用 3 行的最小 MV3 扩展做对照**才确认是浏览器限制而非自己 manifest 出错。
2. `npm i -D jsdom` 静默不装（反复 `up to date` 但 node_modules 不存在）→ 放弃，改 `chrome --dump-dom` 跑真 DOM 断言。
3. **点 checkbox 被误录成「输入 yes」** —— checkbox 也派发 `input`，`el.value` 是 value 属性不是用户输入。被「连续输入应合并成 2 步」这条**具体到值**的断言抓出来；而「录到了 click」这类过程断言全绿。
4. 点提交按钮同时录到 click + submit 两步，回放时第二步必失败 → `onSubmit` 里若上一步是 200ms 内的 click 就丢弃。

### 10:xx `PwaEarnDeduction` 主叫补传 price → **PR #678 已 merge**（2026-07-21 11:37 UTC，merge commit `097f365b`，并入 `feature/sitin4.0`）

> **PR merge 四要素**（最终 2 文件 +19 −3）
>
> **做了什么** —— 违规扣款每分钟调 `pwaEarnDeduction` 扣一分钟收益，原来只传 `orderId`；现在女方主叫时补传 `price`。
>
> **遇到什么问题 → 怎么解决**
> - **怎么区分主被叫** → 不用新加标志，`ConnectSession.price` 天然就是（只在 `startOutgoingCall` 赋值，被叫路径不设），直接透传 `session?.price`。
> - **proto 还没有 price 字段** → 用户说「先处理前端不用管 proto」，按 `double price = 2;` 手工补齐 ts-proto 产物；随后用户在 base 分支重新生成，合并后核对**逐字节一致**，手改被正式产物取代，PR 反而只剩 2 个前端文件。
> - **app-pwa 报一片 `messaging_api` 的 TS2305** → 不是我引入的，是 `business-pwa-proto` 的 **dist 过期**，重新 build 该包即消失。
>
> **残留**
> - [ ] **后端是否真的会用这个字段**未确认 —— 前端传了，服务端有没有读、扣减金额是否按它算，没有验证过
> - [ ] 真机未验：主叫通话中触发 3 次违规 → 看扣减是否按 `price` 算

**需求**：pwa 端**主动发起**通话时调违规扣减接口要传 `price`，被动（被叫）不传。

**⭐ 前端不需要新加主叫标志** —— `ConnectSession.price` 天然就是这个语义：

| 路径 | `session.price` |
|---|---|
| 主叫 `startOutgoingCall` | `options?.price ?? OUTGOING_CALL_PRICE_PER_MIN`，**必有值**（`webCallManager:310` / `nativeCallManager:192`） |
| 被叫 | **不设**（`useWebCall:422` 那个 `price: releasePrice` 只传给接听弹窗展示，没写进 session） |

所以 `pwaEarnDeduction(orderId, session?.price)` 一行就区分了主被叫，判定逻辑一行不用加。

**为什么只有主叫要传**（`callerPayout.ts` 注释即证据）：被叫是通话中逐分钟入账、服务端握着单价；**主叫这一单的钱只在 `finishCallOrder` 一次性入账**，通话进行中服务端不知道单价，扣一分钟收益算不出金额。

**改动 3 处**
- `app-pwa/src/http/callApi.ts` — `pwaEarnDeduction(callOrderId, price?)`
- `app-pwa/src/hooks/useCallViolationDeduction.ts` — 传 `session?.price`
- `business-pwa-proto/src/gen/archat_api/user_api.ts` — **手工同步生成产物**加 `price`

**手改生成产物 → 已被正式产物取代（同日闭环）**

提 PR 时 proto 仓库里 `PwaEarnDeductionRequest` 还只有 `call_order_id = 1`。用户说「先处理前端不用管 proto」，所以我按 `double price = 2;` 假设手工补齐了 ts-proto 产物的 interface / createBase / encode / decode / fromJSON / toJSON / fromPartial 七处，类型对齐 `FinishCallOrderRequest` 的 `double price = 5`，wire tag = `(2<<3)|1 = 17`。

- ⭐ **git merge 对「双方添加了完全相同的行」是自动合并、不报冲突的** —— 省事，但**必须逐处确认没有重复字段**（细微的缩进差异就会变成两份）。已核对 encode/decode/fromJSON/toJSON/fromPartial 各只有一份。

- 教训留存：`src/gen` 入 git、`dist` 不入；`build` 不会自动重新生成（只有 `proto:gen` / `proto:online` 会）。**改了 `src/gen` 必须 build 这个包**，否则 app-pwa 引的还是旧 dist。

### 14:xx native 通话接入陀螺仪端能力 → **PR #686**（`personal/zz/pwa-call-sensor` → `feature/sitin4.0`，2 文件 +59 −1）

**需求**：native 通话缺 `registerSensor` / `unregisterSensor` 两个端能力调用，通话开始注册、判定完分发与否后注销；用户提示「去看 Android 代码确认参数和用法」。

**⭐ 查证 Android 源码后发现这不只是补调用，而是一个真实的判罚缺陷**

`handleNativeCallEnd` 的判罚是「陀螺仪未启用 **且** 露脸率低 → 关闭分发」，但 `registerSensor` **从未被调用过** → 端上永不回调 `onHoldingStateChanged` → `isHoldingRef.current` **恒为 false** → `!isHoldingRef.current` 恒成立 → **判罚退化成「只看露脸率」**。本该因「举着手机」被放过的用户会被误判关闭分发。JS 侧的 handler 和判罚分支其实早就写好了，缺的只是这对调用。

**端上语义**（`PwaNativeInterface` + `utils/SensorEventManager.kt`，均在 `GraceChat-Earn-Android/haven`）
- **`params` 两个方法都不读**，传空串即可（印证用户写的 `registerSensor('','callbackId')`）
- 加速度计，15 个采样为窗算 **z 轴方差 > 0.004** 判「手持」；持续 **60s** 无晃动回落
- **只在状态翻转时回调**（`if (isHolding != newState)`）→ **全程静止会一次回调都没有，收不到 ≠ 出错**
- 首次判定需攒满一窗（`SENSOR_DELAY_UI`，约 1s）→ **注册必须尽早**
- `stop() → pause()` 里复位了 `start` 标志 → 可反复 register/unregister（我一开始担心 `if (start) return` 会导致第二次注册失效，读完 `pause()` 才排除）

**接入点**：`handleNativeCallBegin`（接通即注册）+ `handleNativeCallEnd` 的 `finally`（判罚读完 `isHoldingRef` 之后注销，且异常路径也覆盖）。

**⭐ 两处刻意不加，理由比加更值得记**
1. **取消/超时路径不加** —— 未接通（`duration: 0`），注册只发生在接通时，不会有残留。
2. **事件订阅 effect 的 cleanup 不能加** —— 它依赖 7 个 `useCallback`，通话中会随 `remoteUserInfo` 等变化**反复重建**，cleanup 会在通话中途触发，加了会**误注销正在用的传感器**。组件卸载由端上 lifecycle observer（`onDestroy → stop()`）兜底。

**沉淀**：**「注册/注销成对」的清理位置不能想当然放进 effect cleanup** —— 先看那个 effect 的依赖稳不稳定。依赖里有随 props/state 重建的 `useCallback` 时，cleanup 是「每次依赖变化都跑」，不是「组件卸载才跑」。

**残留**：真机待复测 —— 通话中举手机应见 `Holding state changed: true`；露脸率低但全程举着手机时**不应**再关闭分发。

**顺手修**:`onKeyboardHeightChanged1`(Android<30)判显隐用的 `height > 400` 比的是**转换前的物理像素** —— `.px` 扩展实为 `this / density`(**px→dp,名字反着**)。density=3 的屏上 400px 才 133dp、density=2 上是 200dp,阈值随屏幕密度漂移。改成 `heightDp > 150`。
