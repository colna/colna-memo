## 工作日志 — Snapchat 接入 Social-Proxy 技术方案 v0

- **做了什么**:在 `personal/zz/sp-snapchat` 分支产出 `packages/app-social-proxy-server/docs/snapchat-integration-zh.md`(532 行)—— 参照 IG 现有接入蓝图,给出 Snapchat 接入 V3 Signal 管道的技术方案(未改任何代码)。
- **核心决策**:
  1. **平台维度用字段而非枚举分裂** —— `sp_v3_signal/todo/behavior_log` 加 `platform TEXT` 列(默认 `'instagram'` 平滑存量);`TodoType`/`BehaviorType` 全部复用,新增仅 `SignalType.SC_*`(SC_DM_RECEIVED / SC_ADD_BACK_COMPLETED / SC_NEW_MESSAGE 等)+ APK 脚本映射二维化。
  2. **消息日志表 `ig_message_log` 重命名 `sp_message_log` + platform 列** —— aichat chatHistory 一查通;IG/SC 数据同构。
  3. **设备维度倾向"分开"** —— IG 一台 + SC 一台,避免 APK 频繁切 app;代价是 `todo:lock:{creatorId}` 拆成 `{creatorId}:{platform}`,评审必须确认。
  4. **Rule 表按 platform 分派内嵌** —— `SIGNAL_TO_DEFS[SC_DM_RECEIVED] = [ChatGateDef, ReplyDmDef]`;每个 def 内部 `expandInstagramSteps` / `expandSnapchatSteps` 子函数,主 expand 只分派(避开 SP 的 complexity=15 lint 限)。
- **关键差异澄清**(SC vs IG):无稳定 mid → 去重降级 `(clientChatId, timestamp)`;"Follow" 语义 = "accept friend request"(APK 方法 `acceptSnapFriendRequest`);阅后即焚 Snap/Story Phase 1 不入 rule 表只归档;SC rate-limit 严 → REPLY_DM 30s / SEND_DM 60s / FOLLOW_BACK 45s(vs IG 现值)。
- **里程碑**:M1 骨架(migration + 类型系统 + adapter 壳,IG 全套零回归) → M2 SC DM 回复(白名单灰度) → M3 SC 首私 + 加好友。Phase 2 (发 Snap / Story / 实时监听 / 号池)不在本方案。
- **未决点(评审前必须锁)**:R1 mid 缺失去重契约、R3 lock 拆不拆(取决于设备方案)、R6 `ig_message_log` 外部消费者、APK 契约方法名(`openSnapChat` / `getSnapChatMessages` / `sendSnapChatMessage` 等 7 个)。
