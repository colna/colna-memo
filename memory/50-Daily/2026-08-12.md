# 2026-08-12

## 工作日志 — 13:54(sitin-next2 Snapchat:NEW_MESSAGE 事件 data 改为 object)

**做了什么**:`packages/app-ins-scripts/src/snapchat/actions/startDMListener.js` 的 `reportNewMessage` 上报 NEW_MESSAGE 时,去掉外层 `JSON.stringify`,直接把 payload 对象传给 `bridge.emitScriptEvent({...})`。

**为什么**:`emitScriptEvent(data)` 内部会 `JSON.stringify({success,data,interaction,timestamp})`。原来调用方又先 `JSON.stringify(payload)` 一次 → 事件里 `data` 变成**字符串**(后端要双重 parse)。后端需要 `data` 是 **object**。IG 版 `instagram/actions/startDMListener.js:132` 本就是传对象,Snapchat 改成一致。

**结果**:`node scripts/build.mjs` 通过(snapchat 3 bundle/31 脚本);产物 `dist/snapchat/automation.js` 已是 `emitScriptEvent({platform,type:"NEW_MESSAGE",source,threads})`。事件形如 `{"success":true,"data":{...对象...},"interaction":true,"timestamp":...}`。未提交(规范模式,待用户批准)。

**遗留观察(未改,待用户决定是否统一)**:同仓另有两处仍 `JSON.stringify` 后传 emitScriptEvent —— `snapchat/methods/getChatMessages.js:838`、`instagram/methods/getChatMessages.js:942`。属另一类事件消费方,本次只按用户要求改了 NEW_MESSAGE。

## 工作日志 — 14:0x(sitin-next2:emitScriptEvent 全部改传对象)

**做了什么**:承接上一条,把剩余两处仍 `JSON.stringify` 后传 `emitScriptEvent` 的 CHAT_HISTORY(空批次)上报也改成直接传对象:
- `snapchat/methods/getChatMessages.js:838`(CHAT_HISTORY,字段 platform/type/chatId/data:[])
- `instagram/methods/getChatMessages.js:942`(CHAT_HISTORY,字段 platform/type/chatId/manSocialId/womanSocialId/creatorId/manSocialNickname/data:[])

**为什么**:统一「事件 `.data` 为 object」。`emitScriptEvent(d)` 内部会对整包 `{success,data:d,interaction,timestamp}` 做一次 stringify;调用方再 stringify 就成了字符串,后端要双重 parse。对齐 feature/sp IG 的既有形态(IG startDMListener 本就传对象)。

**结果**:全仓 `grep emitScriptEvent(JSON.stringify` 无残留;5 处 emitScriptEvent 调用全部传对象(startDMListener×2、getChatMessages×2、executeAction 透传包装×1)。`node scripts/build.mjs` IG(3 bundle/38 脚本)+ SC(3 bundle/31 脚本)均通过。未提交(规范模式)。

**注意**:CHAT_HISTORY 载荷自身有个 `data:[]` 字段(消息数组),改完后事件形如 `{success:true,data:{...,type:"CHAT_HISTORY",data:[]},...}` —— 外层 data 是对象、内层 data 是消息数组,是既有 schema,本次只改类型不动字段。
