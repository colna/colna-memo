## 工作日志

### 14:xx videoTips 任务完成后补「完成动作链」（跳会话）

**为什么**：videoTips 通话结束后，前端只做了两件事 —— 发 `phone_call_message`（带 PENDING taskId）+ 删卡。而**正常回消息完成任务**那条链后面还有一整套收尾：`doJump()` → 红灯出 Next unread 按钮（+90s 兜底自动跳）/ 非红直接 `handleTaskComplete()`（清云端倒计时 + 乐观摘 taskQueue + 跳下一个会话）。videoTips 一样都没走，完成后人就干在原会话里。用户确认「要」补齐。

**改了什么**（`packages/app-pwa/src`，5 个文件、纯新增 86 行）：

1. `utils/eventBus.ts` 新增 `CALL_SETTLED` —— 语义是「通话收尾的**串行弹窗全放完**、屏幕让出」，区别于 `CALL_ENDED`（只是通话断了，后面还有一串 await 的弹窗）。
2. `hooks/useNativeCall.tsx` / `useWebCall.tsx`：在结算弹窗 + 奖励弹窗（web 还多一对「通话过短 / 收益失败」）都 await 完之后 emit `CALL_SETTLED`。
3. `services/videoTipsCall.ts`：新增 `pendingJump` / `settled` 两个标记 + `takeVideoTipsPendingJump()`（一次性消费，**两个信号都齐才给**）。
4. `pages/Chat/index.tsx`：`doJumpRef` + 一个 effect，在 `CALL_SETTLED`、`VIDEO_TIPS_CALL_RECORDED`、**以及挂载时**各试一次消费，取到就 `doJump()`。

**关键设计点（都是查出来的，不是想出来的）**：

- **为什么不挂 `VIDEO_TIPS_CALL_RECORDED` 直接跳**：读 `useNativeCall.tsx:255-300` 发现结算弹窗是 `await showCallRecordModalAsync()`（最多 20s）、奖励弹窗 `await showRewardModalAsync()` 也是串行 await 的。RECORDED 在通话一断就发，那时弹窗还没开始播，此刻跳会话会把结算界面撕掉。
- **为什么不用「订阅 modalStore、等没有弹窗了再跳」**：`navigate(getReturnPath())` 和开弹窗之间隔着 React 渲染，Chat 挂载那一瞬弹窗数是 0 → 会抢跑。必须用收尾链末尾的显式事件，不能靠轮询状态推断。
- **⭐ 为什么要「两个信号凑齐」而不是只认 `CALL_SETTLED`**：差点又栽在没验证的时序假设上。`phone_call_message` 是**异步网络发送、发成功才 emit RECORDED**；而**取消 / 未接通**的通话 `callRecordParams` 为空 → 两个弹窗块**全跳过** → `CALL_SETTLED` 紧跟 navigate 就发了，**比 RECORDED 更早**。按产品口径「拨出即算任务完成」这条路径也要跳，只认单边必然静默丢失。所以两个标记先后不固定，改成谁最后到谁触发。
- **`settled` 必须在 `startVideoTipsCall` 里清零**：上一通若是普通通话，它的 `CALL_SETTLED` 会把 `settled` 置位并一直留着，本通一 RECORDED 就立刻凑够两个信号 → 在结算弹窗还开着时抢跳。（同一类问题第 N 次出现：**全局标记必须有归属 + 在使用那一刻复验**，见 07-18 的 P2。）
- **挂载时补一次消费**：通话期间 chat 是卸载的，两个事件都可能落在它重新挂上之前。信号存在 service（模块级单例）里不会丢，chat 只是在几个时机去「取」。

**验证**：`tsc --noEmit` + `pnpm --filter @heyhru/app-pwa lint` 均通过。未提交、未推送。

**沉淀**：这次是**先查证再下结论**的正面例子 —— 三个设计点（弹窗是 await 的、navigate 与开弹窗有渲染竞态、取消路径没有结算弹窗）全部是读了 `useNativeCall.tsx` / `useWebCall.tsx` 源码确认的，其中「取消路径时序反转」如果按直觉写就是一个静默失效的 bug。对照 07-18 连着三次「没查证就下结论」，方法上的区别很明确。
