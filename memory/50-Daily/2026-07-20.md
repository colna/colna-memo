### 14:xx videoTips 任务完成后补「完成动作链」（跳会话）

**为什么**：videoTips 通话结束后，前端只做了两件事 —— 发 `phone_call_message`（带 PENDING taskId）+ 删卡。而**正常回消息完成任务**那条链后面还有一整套收尾：`doJump()` → 红灯出 Next unread 按钮（+90s 兜底自动跳）/ 非红直接 `handleTaskComplete()`（清云端倒计时 + 乐观摘 taskQueue + 跳下一个会话）。videoTips 一样都没走，完成后人就干在原会话里。用户确认「要」补齐。

**改了什么**（`packages/app-pwa/src`，5 个文件、纯新增 86 行）：

1. `utils/eventBus.ts` 新增 `CALL_SETTLED` —— 语义是「通话收尾的**串行弹窗全放完**、屏幕让出」，区别于 `CALL_ENDED`（只是通话断了，后面还有一串 await 的弹窗）。
2. `hooks/useNativeCall.tsx` / `useWebCall.tsx`：在结算弹窗 + 奖励弹窗（web 还多一对「通话过短 / 收益失败」）都 await 完之后 emit `CALL_SETTLED`。
3. `services/videoTipsCall.ts`：新增 `pendingJump` / `settled` 两个标记 + `takeVideoTipsPendingJump()`（一次性消费，**两个信号都齐才给**）。
4. `pages/Chat/index.tsx`：`doJumpRef` + 一个 effect，在 `CALL_SETTLED`、`VIDEO_TIPS_CALL_RECORDED`、**以及挂载时**各试一次消费，取到就 `doJump()`。

**关键设计点（都是查出来的，不是想出来的）**：

- **为什么不挂 `VIDEO_TIPS_CALL_RECORDED` 直接跳**：读 `useNativeCall.tsx:255-300` 发现结算弹窗是 `await showCallRecordModalAsync()`（最多 20s）、奖励弹窗 `await showRewardModalAsync()` 也是串行 await 的。RECORDED 在通话一断就发，那时弹窗还没开始播，此刻跳会话会把结算界面撕掉。
- **为什么不用「订阅 modalStore、等没有弹窗了再跳」**：`navigate(getReturnPath())` 和开弹窗之间隔着 React 渲染，Chat 挂载那一瞬弹窗数是 0 → 会抢跑。必须用收尾链末尾的显式事件，不能靠轮询状态推断。
- **⭐ 为什么要「两个信号凑齐」而不是只认 `CALL_SETTLED`**：差点又栽在没验证的时序假设上。`phone_call_message` 是**异步网络发送、发成功才 emit RECORDED**；而**取消 / 未接通**的通话 `callRecordParams` 为空 → 两个弹窗块**全跳过** → `CALL_SETTLED` 紧跟 navigate 就发了，**比 RECORDED 更早**。按产品口径「拨出即算任务完成」这条路径也要跳，只认单边必然静默丢失。所以两个标记先后不固定，改成谁最后到谁触发。
- **`settled` 必须在 `startVideoTipsCall` 里清零**：上一通若是普通通话，它的 `CALL_SETTLED` 会把 `settled` 置位并一直留着，本通一 RECORDED 就立刻凑够两个信号 → 在结算弹窗还开着时抢跳。（同一类问题第 N 次出现：**全局标记必须有归属 + 在使用那一刻复验**，见 07-18 的 P2。）
- **挂载时补一次消费**：通话期间 chat 是卸载的，两个事件都可能落在它重新挂上之前。信号存在 service（模块级单例）里不会丢，chat 只是在几个时机去「取」。

### 15:xx 修「主动打电话结算永远 $0.00」（两个独立缺陷）

**现象**：女方主叫通话结束，结算弹窗恒显示 $0.00，即便 Total Duration 1min、Qualified Minutes 1min、无违规。

**根因 A（主因，主叫必现）**：`useCallSettlement.getCurrentOrderEarned` 的 `earned` 不是算出来的，是**余额差** `curCash - originCash`。而**女方主叫这一单的钱只在 `finishCallOrder` 时一次性入账**（`callerPayout.ts:22` 既有注释：主叫通话没有任何一端在通话中调 addMoney）。偏偏关单是 `void finishCallOrder(...).catch()` —— **fire-and-forget，没人等它**，紧接着结算就 `refreshCash()` 读余额。两个并发 RPC，钱还没落库，差值恒为 0。
- **为什么只有主叫暴露**：被叫是通话中逐分钟入账，结束时余额已包含，差值法成立。差值法本来就是为被叫设计的，主叫套用就踩时序。
- **修法**：`outgoingCallOrder.ts` 加一个 web/native 共用的闸门 `trackOrderClose()` / `waitOrderClosed(timeoutMs=5000)`，两个 manager 关单时登记 promise，`getCurrentOrderEarned` 读余额前先 await。
- **超时是硬要求**：这个 await 卡在结算弹窗**弹出之前**，关单挂起会把整条收尾链吊死（弹窗不出 → CALL_SETTLED 不发 → 会话不跳）。超时放行退回现状，不会更糟。
- **未验证的一环**：`finishCallOrder` 返回时钱是否已落库，取决于后端是否同步入账。proto 里 `FinishCallOrderResponse` 只有 `code`/`message`，**不返回金额**，前端拿不到权威值，只能"先关单再读余额"。若后端入账是异步的，await 也救不了 —— 需后端确认。

**根因 B（次因，Debug 页拨出必 0）**：默认单价**两套口径**。展示走 `setOutgoingCallPrice(options?.price ?? OUTGOING_CALL_PRICE_PER_MIN)`（0.2），结算走 `connectSession.price = options?.price`（**无默认**）→ `resolveCallerPayout` 的 `?? 0`。不传 price 时**界面显示 $0.2/min、结单按 0 结**。修法：默认值落到 `session.price` 赋值处，两端同源。
- videoTips 不受 B 影响（传了真实单价）；且它传 0 时 `??` 兜不住（0 非 nullish），已由 `Chat/index.tsx:1135` 的不发卡守卫拦住。

**沉淀（⭐ 复用价值高）**：
1. **「兜底值落在哪一层」决定它是否真的生效** —— 同一个默认值在展示层兜了、在数据源头没兜，就会分裂成两套口径，而且**界面看起来是对的**，最难查。默认值要落在**唯一真源**上，不要在每个消费点各兜一次。
2. **`void somePromise()` 是时序 bug 的高发点** —— 只要后面有代码依赖它的副作用（这里是"余额变了"），fire-and-forget 就是隐性竞态。搜 `void ` + 紧随其后的状态读取是一条有效的排查路径。
3. **「金额恒为 0」优先怀疑取值时机，而不是取值本身** —— 截图里 Qualified Minutes = 1min 已经证明不是判罚路径，那就说明合格分钟数根本没参与算钱。

**验证**：`tsc --noEmit` + lint 均通过。未提交、未推送。

### 16:xx 修「任务完成后会话锁不开、切不了会话」（PR #662 第三个提交）

**现象**：videoTips 挂断后来了新会话消息，但不自动跳；手动切换弹 "Please handle this message first"。

**排查链（这次是靠证据一步步收敛的，值得复用）**：
1. 手动切换有拦截提示 → 直接证实 `lockRef.current.locked === true`，不用再猜。
2. 用户给的 `ListConversationStates` 响应里**没有当前会话** → 后端已认为它无待办。
3. 读 `chatConvStore.setTaskQueue`：`taskQueue` 全量替换，但 **`chatMap` 是增量合并** —— 只更新 states 里出现的会话，**缺席会话的 convState 原样保留**。
4. Chat 的 `pendingTask` 由 convState 派生 → 解锁 effect 第一行 `if (pendingTask?.id) return` 直接返回 → 锁永不解开。

**根子是判据选错**：`pendingTask` 来自本地缓存的旧 convState，`taskQueue` 来自服务端最新响应，两者打架时解锁逻辑**选择相信旧的那个**。真正对的那行 `if (taskQueue.includes(conversationId)) return` 排在后面，永远到不了。

**修法**：`setTaskQueue` 里加 `clearAbsentConvTasks()`，把缺席会话的 `convState.tasks` 清空，让 chatMap 与服务端对齐。只清 tasks 不清整个 convState（status / totalEarnedCents 服务端不每轮重发）。

**为什么不靠既有补偿路径**：`chatConvManager:161-165` 有「刷新从 taskQueue 消失的会话」的逻辑，但它**只遍历 `prevTaskQueue`** —— 而 `handleTaskComplete` 会**乐观地把当前会话移出 taskQueue**，一旦乐观移除先发生，下轮 prevTaskQueue 里就没它了，补偿静默失效。两个机制互相踩。

**排除的误清风险（查证过程本身值得记）**：担心接口异常返回空 states 会把所有 task 误清。追到 `web-util-http/HttpClient.ts` 确认请求失败是 `throw e`，被 `chatConvManager` 的 try/catch 接住，**根本走不到 setTaskQueue**。能进到清空逻辑的 states 为空 = 「所有任务都完成了」，正是该清的场景。且 `taskQueue` 本就是全量替换、承担同样语义，本次只是让 chatMap 与它一致，未引入新风险类别。

**沉淀**：
1. **两个数据源描述同一件事时，要明确谁是权威**。这里 convState（本地缓存）vs taskQueue（服务端最新）都能回答「有没有待办」，代码却让缓存赢了。类似结构以后要先问：判据取自哪一侧、过期的那侧会不会赢。
2. **增量合并的容器里，「消失」是一种需要显式处理的信号**。只在「出现」时更新、「消失」时什么都不做，就会留幽灵数据。补偿逻辑若依赖另一个会被乐观修改的状态（prevTaskQueue），等于没兜住。
3. **有用户可见的拦截提示时，先用它定位**，比读代码猜快得多 —— 提示出现即证明锁态，直接砍掉一半假设空间。

### 17:xx 修「红灯任务完成后 Next unread 不出现 + 会话锁死」（PR #662 第四个提交）

**现象**：videoTips 挂断后既不自动跳、也没有 Next unread 按钮，手动切换弹提示，只能刷新。日志里 `pendingTaskId: null` 且**没有 🔓**，却一直「🚫 自动切换被锁拦下」。

**缺陷 1：`activateNextUnread` 一次性快照，目标未就位就永久放弃**
在 `doJump` 那一刻读 taskQueue/chatMap，`others.length === 0` 直接 return。而通话刚结束时 `chatConvManager` 还在 `await IMManager.getConversation()` 逐个把新会话补进 chatMap，此刻 `id in chatMap` 为 false → 按钮不出、90s 兜底也不起，**而它只有 doJump 一个调用点，错过即永久卡死**。videoTips 必现（CALL_SETTLED 紧跟通话结束），普通任务窗口窄、偶发。

**缺陷 2：解锁 effect 用了 `taskQueue` 却不订阅它**
`useChatConvStore.getState().taskQueue` 命令式读取，依赖数组里也没有它。首次运行时若 taskQueue 恰好还含本会话就 return，之后 taskQueue 更新 **effect 不再重跑** —— `lockRef` 是 ref，它的变化同样不触发重渲染，锁再没机会解开。外层第 173 行明明订阅了 taskQueue 并作为 prop 传下来，这个 effect 却绕过去 getState()。

**修法**：1) 改为置 `awaitingNextUnread` 标记 + effect 跟着「已就位的其他会话数」重算；新任务到达时连标记一起清。2) 订阅 taskQueue 并加入依赖。

**有意的行为变化**：等待目标就位期间锁是开的（可手动切）。原先靠 `if (nextUnreadInfo) return` 在红灯等待期保持锁，但那前提是**按钮已经出来了**；目标迟迟不来还锁着毫无意义，正是本次卡死的成因之一。

**沉淀（⭐ 本轮最高复用价值）**：
1. **effect 里读了什么状态，就必须订阅什么状态**。`getState()` 命令式读取 + 依赖数组遗漏 = 这个 effect 只在别的依赖变化时才「顺便」重新判断，判据本身的变化它看不见。这次和上午那个「convState vs taskQueue 谁是权威」是同一类：**判据与触发源脱节**。
2. **ref 的变化不触发 React 重跑**。`lockRef.current` 在依赖数组里毫无作用（引用恒定），把 ref 写进依赖数组容易造成「我已经处理了依赖」的错觉。
3. **「一次性快照 + 早退」是异步补数据场景的通病**。凡是「取当前列表 → 空就 return」的逻辑，都要问：这个列表是不是正在被异步填充？错过这一次还有没有第二次机会？这次是 `id in chatMap`，之前 videoTips 的 CALL_SETTLED/RECORDED 时序也是同一个形状 —— 解法都是**改成响应式重试，而不是赌时机**。

1. 解锁 effect 漏 `awaitingNextUnread` 守卫 —— 把「红灯完成→出按钮」拆两步后多出的窗口，恰好被我新加的 `taskQueue` 依赖唤醒 → 提前解锁 → 自动切换抢走 Next unread。**新加依赖会唤醒此前不会执行的中间态**，拆分状态机时必须重扫所有守卫。
2. `clearAbsentConvTasks` 的全量前提不成立 —— 用户说「是全量」，我就直接信了，**没去读 proto**：`limit` 不传默认只有 **20**。超 20 的会话会被误清 task。**用户的口头确认不能替代查证**，尤其是这种「接口语义」类断言。

**agent 也会幻觉**：报了 `pendingJumpRef` 是死代码，实际有 3 处引用且是既有代码。**agent 结论必须逐条验证**（这次验了 4 条关键的，1 条是假的）。

**⭐ 沉淀（比这个 bug 本身更值钱）**：
1. **「推断」和「查询」有得选时，永远选查询。** 缺席、超时、没返回 —— 这类「以沉默为依据」的判断，前提往往是个没人验证过的隐含约定（这里是 limit 默认 20）。
